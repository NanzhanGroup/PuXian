# 字典 / 序列「严格」口径 · 契约与迁移指引

> **Milestone**：M120（`qg-issue 76`）起 · **本文件覆盖 M116–M167 的严格化族**（最新：M163/M164/M166/M167）
> **定调来源**：本灵 2026-09-15「字典缺键：保持严格」
> **一句话**：**缺键 = 运行时错误 `R1008`，不回退静默 `null`。** 可选键必须**显式守卫**（`.has()`）。
> 同族的严格规则：构造位置非字符串键 ⇒ `R1002`（M163）· `d[非字符串]` ⇒ `R1002`（M164）·
> 迭代期间改容器 ⇒ `R1003`（M166）· 解包形状不符 ⇒ `R1002`（M167）。
> 本文件给出三轨错误码契约、正确写法、存量代码迁移清单与可观测性说明；规范条文见 `spec.md` §17。

---

## 0. 为什么严格（决策留痕）

| 口径 | 后果（实测） |
|---|---|
| **静默 null**（M116 前的编译轨） | 移植 `ws-center` 时 `str(r["role"])`（键缺失）在编译轨得到字符串 `"null"` 并**写进数据库**；解释轨当场报错 ⇒ 同一份源码两轨行为不同，且**静默数据损坏** |
| **严格 R1008**（M116 起三轨统一，M120 起配套完善） | 缺键当场报错、带源位置、退出码非 0 |

**残留代价**：读「可选键」的存量代码会从「能跑」变「崩」——这是**设计意图**（把沉默的错误提前暴露），代价用守卫写法 + 本指引 + 可观测性补齐来付。

## 1. 契约（解释轨 / VM 轨 / C 轨 三轨同码同文）

| 写法 | 场景 | 码 | 消息 |
|---|---|---|---|
| `d["k"]` · `d.k` | dict 缺键 | **R1008** | `字典没有键 'k'` |
| `s.f` | 结构体实例缺字段 | **R1008** | `结构体没有字段 'f'` |
| `x.f` | 其它类型取字段 | **R1007** | `类型 <t> 没有字段 'f'` |
| `x.m(...)` | 类型无此方法 | **R1007** | `类型 <t> 没有方法 'm'` |
| `l[i]` · `s[i]` · `d[i]` | 索引越界 | **R1003** | `列表索引越界: i (len=n)` · `字符串索引越界: i` · `字典索引越界: i (len=n)` |
| `d[i]` | 键不是字符串 | **R1002** | `字典索引键必须是字符串` |
| `d.has(x)` · `d.contains(x)` | 参数不是字符串 | **R1002** | `方法 has 参数 1 需要 string` |
| `d.get(x)` · `d.set(x,…)` · `d.remove(x)` | 参数不是字符串 | **R1002** | `方法 get 参数 1 需要 string` |
| `{k: v}` 字面量 · `{k: v for …}` 推导式 | **键不是字符串**（M163 起） | **R1002** | `字典键必须是字符串，实际是 <t>` |

> **M163（第 49 轮 · 缺陷 168/169）新增最后一行**：修前**只有解释轨报错**——VM 轨与 C 轨
> 在**构造位置**静默丢弃非字符串键（`{1: 11, 2: 22}` 得 `len=0`；`{"a":1,"b":2,3:4}` 得
> `len=2`，只丢那一项），与 R1008 的「静默 null」同族的**静默数据丢失**；推导式上 VM 轨还
> 只是借 `set` 方法的词条报同一码（`方法 set 参数 1 需要 string`）⇒ 三轨同码不同文。
> 修后三轨**同码同文**：`px_dict_set_checked`（C 轨 / VM `DICTSET`）+ VM `NEWDICT` 内联检查
> + 解释轨字面量/推导式两条路径。迁移代价：源码里若有 `{1: "a"}` 这类写法，修前静默得空
> dict、修后**当场报错**——这是**设计意图**（与本章 §0 同一条理由）。

> **M164（第 50 轮 · 缺陷 170）把 `d[i]` 也收进本契约**：修前 `d[0]`（**读取**位置的整数索引）
> **解释轨报 R1002，而 VM/C 轨返回第 0 个键**（M37 为 `for k in d` 迭代内部引入的位置语义，
> `px_index(d, int)` 被**迭代与用户索引共用**）⇒ 三轨分叉，且用户容易把「第 i 个键」误读成
> 「第 i 个元素」。现迭代协议改由**专用入口**提供（C 轨 `px_iter_at` / VM 轨指令 `PXOP_ITERAT`），
> `px_index` 的 dict-int 分支**删除** ⇒ **`d[非字符串键]` 三轨一律 `R1002 字典索引键必须是字符串`**。
>
> | 想做的事 | ✅ 正确写法 | ❌ 不要写 |
> |---|---|---|
> | 取第 i 个键（按插入序） | `d.keys()[i]`（先 `.keys()` 得 list 再索引） | `d[i]`（**R1002**） |
> | 遍历键 | `for k in d` / `[k for k in d]` | —— |
> | 遍历值 | `for v in d.values()` | —— |
> | 遍历键值对 | `for k, v in d.items()`（M167 起；`items()` 返回 `[[k, v], …]` 插入序快照） | `for k, v in d`（**R1002**：dict 直接迭代只产键，见下） |
>
> **已收口**（M166 · 第 52 轮 · 缺陷 176）：**迭代期间修改被迭代的容器**（`for k in d` 里写 `d`、
> `for x in l` 里 `l.append(...)`）修前三轨**四种**行为（解释轨 dict 键快照 / list 活长度；
> VM 轨长度进循环前取一次；C 轨 dict 活长度；且 `l.pop()` / `d.remove()` 在 VM 轨直接越界 rc=1）。
> 现三轨**一条真相**：**进入循环时快照长度**，迭代期间长度变化（增或减）一律
> `R1003 迭代期间被迭代容器长度变化: <n0> → <n1>`。⇒ **不要在迭代中修改被迭代的容器**；
> 要「遍历时过滤/删」就先做快照（`let ks = d.keys()` / `let snap = l[:]`）、用 `d.values()`，
> 或写到**另一个**容器。见 `docs/PUXIAN_CHEATSHEET.md` 事实 194 与 `examples/m166_iter_mutate/`。

> **M167（第 53 轮 · 缺陷 180/182）补上「解包」这一块**：`for a, b in xs`（语句形式，此前 parser 直接
> `E2001`，只有推导式支持解包）与 `dict.items()` 一起落地，并把解包诊断收口为三轨一码一文：
> N ≥ 2 个变量时元素必须是 **list/tuple 且长度恰为 N**，否则
> `R1002 解包需要 list/tuple，实际是 <t>` / `R1002 解包需要 N 个元素，实际是 M`。
> ⇒ **`for k, v in d`（直接迭代 dict）会响亮报 `R1002`**（dict 迭代只产键）——这是**带指引的响亮**：
> 请改写 `for k, v in d.items()`。修前该写法在三轨有**四种**行为（解释轨静默给 null、VM/C 报越界…），
> 与本章 §0 同一条理由：**响亮优于静默**。见 `examples/m167_unpack/`。

> **M165（第 51 轮 · 缺陷 178/179）· 边栏（严格性同族）**：**求值顺序统一为「词法左→右」**
> （表达式 / 函数实参 / 赋值目标→键→右值）。C 标准不规定实参求值顺序 ⇒ 修前 C 轨按 gcc 的**右→左**，
> 于是 `print("A=" + str(l.pop()) + " len=" + str(len(l)))` 这类**同表达式多处副作用**的代码在三轨得到
> **不同结果值**。⇒ 写码时不要依赖「未定义的求值顺序」；需要顺序就拆语句。见 `examples/m165_eval_order/`。

**退出码**：非协程路径失败 → `1`；协程内失败 → 打印现场后**隔离**（宿主继续），但**进程正常退出时返回 1**（M120 起，见 §4）。

> `R1008` 与 `R1007` 的分工：**「缺键/缺字段」= R1008**（数据缺失），**「类型没有这个方法/字段」= R1007**（能力缺失）。

## 2. 正确写法

### 2.1 可选键（state 文件 / 配置 / 请求头）

```px
# ❌ 生产 state 无该键 → R1008，服务启动即崩
if st["update_fail_date"] == td and st["update_fail_count"] >= MAX_UPDATE_FAIL_PER_DAY:
    ...

# ✅ 每个裸取都先守卫
if st.has("update_fail_date") and st["update_fail_date"] == td \
   and st.has("update_fail_count") and st["update_fail_count"] >= MAX_UPDATE_FAIL_PER_DAY:
    ...
```

**推荐**：把守卫集中成一个取值助手，业务代码只见局部变量，避免"守卫一处、裸取三处"：

```px
def st_str(st, k, dflt):
    if st.has(k):
        return str(st[k])
    return dflt

def st_int(st, k, dflt):
    if st.has(k):
        return int(st[k])
    return dflt
```

### 2.2 嵌套 dict

```px
# ❌ cfg["db"]["host"] —— 任一层缺键即崩
# ✅ 逐层守卫（父键不存在时短路，不会继续取子键）
if cfg != null and cfg.has("db") and cfg["db"].has("host"):
    h = cfg["db"]["host"]
```

### 2.3 `env()` / `json_parse()` 可能返回 `null`

- `env("X")` 未设置 → **`null`（不是 `""`）** ⇒ `cfg.has(k)` 在 null 上 → **R1007**。先判 `if cfg != null`；字符串判空用 `== null or == ""`。
- `json_parse("")` → 报错 `json: 无法解析`（不是返回 null）。
- `{}` **字面量得到 `null`**，不是空 dict（空的空 dict 用 `json_parse("{}")`）。

### 2.4 `get` 的默认值只覆盖"键不存在"

```px
d.get("k", 0)      # 键不存在 → 0；键存在但值为 null → 仍返回 null
```

> ⚠️ **缺陷 194（M174 收口）**：这条规则此前**只有解释轨**遵守 —— runtime 侧用
> 「取出的值是不是 `null`」判存在性（`px_is_null(v) && nargs >= 2`）⇒ 编译轨（VM/C）在
> 「**键存在但值为 `null` + 给了默认值**」时返回**默认值**，解释轨返回 `null` ⇒ 三轨分叉，
> 且与本文档相悖。M174 起 runtime 改用 `px_dict_has` 判存在 ⇒ **三轨同一条真相**
> （门 `examples/m174_dict_get/`：12 条语义矩阵 × 三轨逐字节一致 + 1 道负控）。

### 2.5 读字典的三条正路（选哪条取决于「缺键算不算正常」）

| 写法 | 缺键时 | 键存在但值为 `null` | 语义/出处 |
|---|---|---|---|
| `d["k"]` / `d.k` | **`R1008` 运行时错误**（响亮，带源位置） | 返回 `null` | 本文档主口径：**缺键必须显式守卫** |
| `d.has("k")` 再取 | 你自己决定 | `true` ⇒ 取到 `null` | 「有键就用它的值」——**守卫写法** |
| `d.get("k", 默认)` | 返回**默认值** | 返回 **`null`**（不是默认值） | = Go 两值语义 / Python `dict.get`；**M174 起三轨一致** |

**为什么不能「缺键一律给 null」**（历史实锤，M116 D2 的定调来源）：移植 `ws-center` 时
`str(r["role"])`（键缺失）在编译轨下得到字符串 **`"null"`** 并被**写进数据库**，而解释轨当场报错
⇒ **静默的错值比报错危险得多**。故主口径保持严格；确实需要「缺了就按默认值走」的场合，
用 `d.get(k, default)`（现在三轨一致）或 `d.has(k)` 守卫。

> 另注（晨曦附注）：`int_to_hex(n, width)` 的 **width 是必填的**（缺参数会 `R1002`），
> 写成 `int_to_hex(n)` 会当场报错而不是生成错字节 —— 报错在**构造请求字节**这类场景里
> 是好事（否则会打出一个「看起来正常」的畸形请求）。

## 3. 存量代码迁移清单

1. 全量扫裸取：`grep -n '\["' *.px`、`grep -n '\.[a-z_]*\b' *.px`（字段式取键）。
2. 逐个判定该键是否**必然存在**：
   - 来自 `json_parse` / `read_file`+解析 / 状态文件 / 请求头 → **必须守卫**；
   - 本函数内刚 `set` 过的 → 可不守卫。
3. 迁移后**先跑 `px run`**（解释轨）：它是 Mini 子集、启动最快，且与产物同码同文，能最先暴露缺键。
4. 服务类程序：注意 `R1008` 若发生在 handler 协程内 → 客户端拿 **500**（M116 D7），该协程同时终止 ⇒ 用 §4 的观测手段确认。

## 4. 协程错误可观测性（M120 · qg-issue 76 E1/E2）

**问题**（M120 前）：协程内的运行时错误被「隔离」——打印现场后宿主继续。若**顶层工作全部跑在协程里**（服务、轮询器、守护进程的常见形态），进程会**以 `rc=0` 正常退出 = 假成功**：CI 判绿、systemd 不判失败、监控看不出。严格语义被隔离机制吞掉，等于没严格。

**M120 后**：

| 行为 | 说明 |
|---|---|
| 隔离时打印 | `[px-coro] 协程运行时错误已隔离（第 N 次，px-coro）：该协程已终止，宿主继续；进程正常退出时将返回 1` |
| 退出时 | `退出码修正：本次运行有 N 个协程因运行时错误被隔离终止`，进程返回 **1**（原为 0 时） |
| 立即终止语义 | `PX_SPAWN_ISOLATE=0` —— **M120 前该变量在 VM/px-coro 轨完全无效**（只有另一条 `px-spawn` 路径读它），守卫/守护常用默认轨 ⇒ 逃生舱拿不到。M120 起两条路径都尊重 |
| 查询 | C 侧 `px_coro_err_count()` |

## 5. 案例：`ws-core` `check.px:79`

```px
# ❌ M118 重编后启动 3s 内即崩（生产 state 与新建 state 均无 update_fail_date）
if st0["update_fail_date"] == td and st0["update_fail_count"] >= MAX_UPDATE_FAIL_PER_DAY:

# ✅ 守卫版（语义等价：缺键 = 计数为 0 = 未失败过）
if st0.has("update_fail_date") and st0["update_fail_date"] == td \
   and st0.has("update_fail_count") and st0["update_fail_count"] >= MAX_UPDATE_FAIL_PER_DAY:
```
