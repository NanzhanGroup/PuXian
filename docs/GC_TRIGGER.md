# GC 触发与页归还（M317 · 缺陷 551）

> 面向：运维（我的服务为什么一直涨）、库作者（什么时候能指望 GC 跑）、
> 改 runtime 的人（改这里必须同时改什么）。
> 本文的每个数字都来自 `examples/m317_gc_time_trigger/` 里的装置在本机实测（2026-10-21）。

---

## 1 病灶：两条触发判据都是「批处理尺度」的旋钮

`gc_register` 里原本只有两条判据：

| 判据 | 缺省 | 对「长期在线的低流量服务」意味着 |
|---|---|---|
| 对象数 `PX_GC_THRESHOLD` | 1,000,000 | 反代路径实测 **8.9 个对象/请求** ⇒ 要 **11 万请求**才触发 |
| 分配字节 `PX_GC_TRIGGER_BYTES` | 512 MiB | Ma 生产实测 **≈7.6 KB/s** ⇒ 要 **19 小时**才触发 |

两条都打不到 ⇒ **GC 实际上永不运行** ⇒ 垃圾线性累积。本机复现（反代路径，默认参数）：

```
T0 anon=7408KB → 1000: 28472 → 2000: 37720 → … → 6000: 68816 → … → 18000: 160608
[px-gc-stats] dump why=interval runs=0
```

斜率 **10.2 KB/请求**且**永不收敛**。而把字节阈值调小，同一负载立刻平台化：

| 字节阈值 | 6000 请求后 RssAnon |
|---|---|
| 缺省 512 MiB | 68,816 KB（且仍在涨） |
| 4 MiB | 26,940 KB |
| 256 KiB | 23,612 KB |

⇒ **是「该回收的没回收」，不是泄漏。**（这条判断推翻了报障原文里「每请求 2.7KB 泄漏」的表述。）

---

## 2 修复：加两条「何时」判据 + 一条空闲推进 + 一个心跳线程

**只改「何时回收」，回收语义（标记 / 清扫 / slab 复用）一字未动。**

| # | 判据 | 缺省 |
|---|---|---|
| ① | 距上次 GC ≥ `PX_GC_MAX_INTERVAL_MS` | **30000 ms** |
| ② | 自上次 GC 分配 ≥ `PX_GC_TIME_FLOOR_BYTES` | **1 MiB** |
| ③ | 或：上次 GC 后仍有**非头空 slab** 待归还（`g_gc_idle_reclaim`） | 自动 |
| ④ | 空闲 GC 心跳线程：每 1s 调一次 `px_gc_poll()` | 起在 `fserve_ensure` / `px_serve` |

- ① + ② **必须同时满足**。只有 ① 会让空闲服务每 30s 白跑一次「回收 0 个」（O(堆) 纯浪费）。
- ③ 解决「流量停了 ⇒ 不再分配 ⇒ 不再 GC ⇒ 空页永不归还」：`SLAB_FREE_STREAK(4)` 轮的
  空 slab 观测**只能靠 GC 轮次推进**，没有 GC 就永远到不了第 2 轮。
- ④ 解决「谁来调 `px_gc_poll`」：两套 serve 池在没有连接时都阻塞在 `pthread_cond_wait`，
  而 `px_gc_poll()` 只在**处理完一个 job 之后**被调用 ⇒ 空闲时无人推进。
  ⚠️ 不放进 worker 循环的原因：① 两套池要改两处（易漂移）；② `http_serve` 的 worker
  在空闲时会**注销 GC 槽**（F3-fix 防长锁窗口），让它醒来自救会把「注销」语义搅乱。
- 时间判据的时钟用 `CLOCK_MONOTONIC_COARSE`（~5ns，精度 ~4ms），且只在**每分配 256KiB**
  之后取一次 ⇒ 热路径成本 = 一次比较。

`PX_GC_MAX_INTERVAL_MS=0` 可**显式关闭**（回到旧行为），门的「关闭档」就是这么做的。

## 3 效果（本机实测，反代装置）

| 场景 | 修前 | 修后 |
|---|---|---|
| 6000 请求（默认参数） | 68,816 KB，斜率 10.2 KB/请求，`runs=0` | 见下 |
| 3000 请求，`interval=0`（关闭档） | — | 斜率 **8355 B/请求**、`runs=0`（缺陷可复现） |
| 3000 请求，`interval=1s` | — | 斜率 **174 B/请求**（= 关闭档的 **2%**）、`time_runs=9` |
| 90000 请求（≈3min，默认 30s） | 无上限（会一路涨到 512 MiB 才触发一次） | **t=30s 起平台化在 136–141 MB**；**t=120s 回落 141MB → 33MB** |

那条「t=120s 回落」值得单独说：它证明 **页真的会还回去**，只是需要
`SLAB_FREE_STREAK(4) 轮 × 触发间隔` —— 默认参数下 = **约 2 分钟**。修前因为 GC 不跑，
这个「4 轮」永远等不到，所以在生产上看起来就是「永不归还」。

## 4 高水位 = `速率 × 间隔`（这条必须知道）

时间判据**管不住字节**：两次 GC 之间的垃圾全都在堆上。所以

```
稳态高水位 ≈ 存活集合 + min(PX_GC_TRIGGER_BYTES, 分配速率 × PX_GC_MAX_INTERVAL_MS)
```

实测对照（同一装置，约 490 rps × 10 KB/请求 ≈ 4.9 MB/s）：

| 间隔 | 平台高度 |
|---|---|
| 60s | 243 MB |
| 30s（缺省） | **136–141 MB** |
| 1s（门里用的档） | ~30 MB |

⇒ **低流量节点**（Ma 生产 7.6 KB/s）在缺省参数下两次 GC 之间只有 ~230 KB 垃圾，
平台由「存活集合」决定，与间隔无关。
⇒ **高吞吐节点**想压低高水位，两条路：调小 `PX_GC_MAX_INTERVAL_MS`，
或调小既有的 `PX_GC_TRIGGER_BYTES`。**「自适应软上限」尚未做**（见 §6）。

## 5 平台态那几十 MB 是什么（归因，不是猜测）

平台态（缺省参数，经过一轮回落之后）用 `PX_GC_STATS` 的 slab 行 + smaps 逐段量：

| 组成 | 量级 | 可回收吗 |
|---|---|---|
| 线程栈（256 常驻 worker × ~52KB 已触碰） | **13.7 MB** | ❌ 线程活着就在用（T0 时 256 条栈已建好，服务请求后每条约撑大 30KB） |
| slab 映射（21 个 size-class） | ~10 MB 峰值 → **1–2 MB** 稳态 | ⚠️ 部分：**整块空闲**的能 munmap；**部分使用**的不能（无页级回收/无压实） |
| 运行时大块（表/缓冲） | ~6 MB | ❌ 容量型数组，不缩容 |

⇒ 对「低流量节点涨到几百 MB」这条报障，**修复点是 §2 的时间判据**，不是别处。
⇒ 剩下的「部分使用 slab 不归还」是分配器形态问题（要页级回收或对象搬迁/压实），
**本轮不做**，见 §6。

## 6 未做 / 边界（照实登记）

1. **自适应软上限**（`next_trigger ≈ max(floor, 上次回收量 × 2)`，等价 Go 的 GOGC）没做
   —— 它要按上次 GC 的**回收字节数**缩放，而当前 sweep 不算这个量；做之前得先加账面。
2. **页级回收**（对部分使用的 slab 做 `madvise(MADV_DONTNEED)`）没做 —— 空闲槽里存的是
   空闲链表指针，直接 DONTNEED 会把链表打断；要做得先重建链表 + 处理槽区跨页。
3. **`http_serve` 的 fserve worker 空闲时不注销 GC 槽的路径**没动（心跳线程绕开了它）。
4. **GC 耗时随存活对象数增长**：实测 ~500k 对象/120MB 时单轮 >100ms
   （`PX_GC_STATS` 的 `slow` 计数会涨）。这是既有性能面，本轮不设阈值。
5. **门的覆盖边界**：判的是**服务端反代路径**（`http_serve` 里调 `http_request`，
   即 Ma `proxy_routes` 的形状）。纯入站 `http_serve`（handler 直接 200）修前修后都零增长，
   不在判据面内。

## 7 运维速查

```sh
# 看服务端的 GC 读数（服务不退出也能看）
PX_GC_STATS=1 PX_GC_STATS_INTERVAL=30 ./your_app
#   [px-gc-stats] === dump why=interval runs=N skips=0 empty=0 slow=N ===
#   [px-gc-stats] heap alloc_since_gc=…B trigger_bytes=…B max_interval_ms=… time_runs=… idle_runs=… idle_reclaim=… tick=…
#   [px-gc-stats] slab n=… map_bytes=…KB free_slots=… fully_empty=…
#   · runs=0 且 time_runs=0        ⇒ 时间判据没生效（检查是不是设了 PX_GC_MAX_INTERVAL_MS=0）
#   · idle_reclaim=1 且 idle_runs 在涨 ⇒ 空闲心跳在推进（空 slab 正在被还回去）
#   · fully_empty 很大而 n 不降    ⇒ 还没到 SLAB_FREE_STREAK(4) 轮，再等
#   · slow 一路涨                  ⇒ 存活对象太多，单轮超 PX_GC_SLOW_MS（默认 100ms）
```

调参：

| 环境变量 | 缺省 | 作用 |
|---|---|---|
| `PX_GC_MAX_INTERVAL_MS` | 30000 | 时间判据；`0` = 关闭（旧行为） |
| `PX_GC_TIME_FLOOR_BYTES` | 1 MiB | 时间判据所需的**最小垃圾量**（防白跑） |
| `PX_GC_TRIGGER_BYTES` | 512 MiB | 既有字节阈值（**上限**，与时间判据取先到者） |
| `PX_GC_THRESHOLD` | 1,000,000 | 既有对象数阈值 |

## 8 给改 runtime 的人

- 加「触发判据」只允许改**何时**；**不得**改标记/清扫/slab 复用语义。
- 新判据必须能**关掉**（`=0`），否则无法做「关闭档 ⇒ 必须复现缺陷」这类判据。
- 新判据必须写进 `PX_GC_STATS` 的 dump（否则运维看不见，M312 的教训）。
- 改完必跑：`examples/m317_gc_time_trigger` · `examples/m312_gc_lock_order` ·
  `examples/m207_gcstress`（压力筛）· `examples/m170_gc_root_leak` 这一族。
