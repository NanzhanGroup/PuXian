## 三、M89 原版负载复跑（`examples/m89_perf/fib_calc.px`，`BENCH_REPS=5`）

md5 `4085d090734ff84bc0f08ab9773fd3aa`（与清歌所报逐字节一致）。

| 轨 | M89 记录（2026-09-09 · px 0.2.0） | 清歌（2026-10-05 · 0.2.9-m259） | **本机（2026-10-05 · 0.2.17）** | 本机相对 M89 |
|---|---|---|---|---|
| **C 轨** | 6.091 s | 0.28 s | **0.246 s**（5 轮 0.256/0.252/0.247/0.246/0.247） | **24.8× 提速** |
| **VM 轨** | 9.283 s | 1.21 s | **0.913 s**（5 轮 0.920/0.915/0.959/0.940/0.913） | **10.2× 提速** |
| **VM/C** | **1.52×** | 4.32× | **3.71×** | 比值**被拉大 2.4×** |

**✅ 清歌的量级确认**（其报 21.8×/7.7×，本机 24.8×/10.2×；同机同型号 CPU，差值 10–25% 属版本/频率档差异）。

**归因复核（清歌的推断）**：
```c
// C 轨产物 fib_calc.c（本机实查）
return px_call(px_get_global("fib"), …);      // 每次递归 = 一次全局名解析
```
M105-S2 把 `px_get_global` 从"线性 `strcmp` 扫描（平均 331.6 项探测）"改为 **O(1) 哈希表**
（`strcmp` −99.6%）—— **两轨都在付这笔钱，C 轨调用更密、付得更多** ⇒ 绝对提速更大、比值反而拉开。
**结论：清歌的归因成立。**

## 四、⭐ 新发现：**基线生成器自己已经失真**（本轮最重要的结构性发现）

`examples/m89_perf/bench_vm_vs_c.sh`（M89 写的"默认轨切换决策数据"生成器）里这两行：

```bash
"$PX" build     fib_calc.px   && cp build/fib_calc "$BIN/fib_calc_c"     # 标签 c
"$PX" build --vm fib_calc.px  && cp build/fib_calc "$BIN/fib_calc_vm"    # 标签 vm
```

**M91 把 `px build` 的默认轨从 C 切成了 VM**，而 `--vm` 成了**同义冗余 flag**（`tools/px:107` 明确写着
"VM 轨（M91 起 = 默认，flag 保留兼容）"）⇒ **两条命令产出的都是 VM 轨**。

实测（本机，同机器同轮）：

| 脚本里的标签 | 实际命令 | `fn_fib` 符号 | 5 轮 min |
|---|---|---|---|
| `fib_calc_c`（"C 轨"） | `px build` | **0**（= VM 轨） | 0.951 s |
| `fib_calc_vm`（"VM 轨"） | `px build --vm` | **0**（= VM 轨） | 0.958 s |

⇒ 该脚本现在测的是 **VM vs VM（1.007×）** —— 它**既测不出 1.52×，也测不出 3.71×**。

**为什么没人发现**：`grep -rn m89_perf` 在 `selfhost/gates.registry.sh`、`.github/workflows/ci.yml`
与全部 `examples/*/verify.sh` 里 **0 命中** ⇒ **这份"决策数据底座"的生产脚本从未被任何门跑过**。

> 📌 这是本仓同一形状的**第 N 次**（M251 孤儿门、M259 本地≠CI、M223 选料不可判定）：
> **没有判据的自动化 = 迟早静默腐烂，且腐烂时无人知晓。**
> 与清歌 §2.5 的判断合起来看：**过期基线比没有基线更危险** —— 现在还要加一句：
> **产生基线的脚本本身也会过期，而且它比数字更隐蔽。**

**处置**：本轮回修脚本（`--vm` → `--c`，并加产物判别自检）；并在 §九 把它纳入性能门。

## 五、微基准全谱（本机 v2 基线 · 8 负载 × 双轨）

方法同 §2.3。**这是本机第一组、可被性能门直接引用的数字。**

| # | 负载 | 形状 | VM (s) | C (s) | **VM/C** | 清歌 VM/C | stdout 一致 |
|---|---|---|---|---|---|---|---|
| 1 | `fib28`（×5 递归） | 纯递归 | 0.961 | 0.264 | **3.64×** | 4.11× | ✅ |
| 2 | `fib26`（×5） | 纯递归 | 0.374 | 0.103 | **3.63×** | 4.50× | ✅ |
| 3 | `while_sum` 3M | 算术/比较/JMP | 0.333 | 0.064 | **5.20×** | 6.67× | ✅ |
| 4 | `loop_sum` 3M（`range` 物化） | 迭代 + 物化 | 0.298 | 0.113 | **2.64×** | 2.54× | ✅ |
| 5 | `mixed` 20 万（dict+list+str） | 容器 | 0.505 | 0.524 | **0.96×** | 0.97× | ✅ |
| 6 | `jsonwb` 2 万对象 构→串→解 | JSON | 1.380 | 1.440 | **0.96×** | 1.01× | ✅ |
| 7 | `textscan` 3 万行 split+contains+regex | 文本 | 0.067 | 0.076 | **0.88×** | 0.76× | ✅ |
| 8 | `stridx64k` 65 540 字符逐字符索引 | M106 场景 | 0.228 | 0.242 | **0.94×** | 0.96× | ✅ |

**启动**：空程序 200 次连跑 = 0.305 s ⇒ **1.53 ms/次**（清歌 2.30 ms）。
**热构建**：0.54 s（清歌 0.76 s）。冷构建本轮未测（会打断并行全量门的缓存，见 §十）。

### 读法（决定"要不要走 `--c`"的唯一依据）

```
纯计算 / 深递归  →  VM 慢 2.6–5.2×   ⇒ 用 --c 有意义
容器 / JSON / 文本 / 大串  →  VM/C = 0.88–0.96×  ⇒ **C 轨不更快，甚至更慢**
```

⇒ 与 M104"成本主体是**动态值层**而非分派层"的结论**一致**：
纯计算把"值层开销"摊在算术上所以差距大；容器/字符串负载**本身就活在值层里**，两轨拉不开。

> ⚠️ **因此 `--c` 的正确说法是**："纯计算热点约 **3.6×**（不是 1.5×）；容器/文本负载**无收益**。"
> 现值 `tools/px:113` 写"纯计算热点程序用 ≈ 1.5x 性能" —— **两个方向都错**（幅度低估、
> 且没提"多数负载无收益"）。本轮修正。

## 七、字符串 `+=` 是 O(n²)（运行时层 · 三轨同病）

本机复跑（VM 轨产物，3 轮取 min）：

| n | `s += "x"` | `list.append` + `join` | 差距 | 晨曦数据（`+=`） |
|---|---|---|---|---|
| 7 500 | 25.9 ms | 4.7 ms | 5.5× | 33 ms |
| 15 000 | 81.2 ms | 6.2 ms | 13× | 99 ms |
| 30 000 | 463.6 ms | 8.5 ms | 55× | 616 ms |
| 60 000 | **1 950 ms** | 13.8 ms | **141×** | 2 937 ms |

**n 翻倍 ⇒ 耗时 ≈ 3.1× / 5.7× / 4.2× ⇒ 确证 O(n²)**（`append+join` 侧 4.7→6.2→8.5→13.8 = 线性）。
**✅ 晨曦数据逐点同量级确认。**

**性质**：这是**运行时层**（`px_add` 的 STR+STR 分支：每次分配新缓冲并整体复制），
**三条轨都受影响** —— 不是解释器的问题，也不是 VM 的问题。

⇒ **M270 已收口（常数部分）**：改为**单次分配**（分配 2→1、整串拷贝 2→1）
⇒ 大 n 段实测 **1.73–1.98×**（n=30 000：463.6 → **233.6 ms**；n=60 000：1 950 → **1 128 ms**）。
⚠️ **复杂度未变**（仍是 O(n²)）—— 原因是**表示的硬约束**：
`str.data` 内联在 `LXObject` 之后的同一块内存里 且「`PX_STR` 恒不可变」是全仓不变量
⇒ **就地扩容结构上不可能**；而 CPython 那套「引用计数唯一 ⇒ 原地 realloc」**搬不过来**
（本运行时没有对象级引用计数，`var x = s` 这种别名没有任何记录）。
⇒ 复杂度的正解（引用计数 **或** 所有权/逃逸分析）属**独立立项**。
详情见 **`docs/STR_CONCAT.md`**。

## 九、性能回归门的设计（供 M267 立项）

### 9.1 为什么必须要门

- 全仓 **179 个门全是正确性门**（`grep -c '^run ' selfhost/gates.registry.sh` = 179；无一性能判据）。
- M105/M106/M107 的三笔收益（1.88× / 1.78× / 5.6×）**全靠人工量化** ⇒ 后续任何重构都可能悄悄退回去。
- 本轮实证：连**生成基线的脚本**都烂了 8 个月（§四）而无人知晓。

### 9.2 门的设计要点（按"避免假阳/假阴"取舍）

| 要点 | 做法 | 理由 |
|---|---|---|
| **判据形态** | 报**相对基线的 ×倍**，不报绝对秒 | 机器/负载会变，绝对值不可跨环境 |
| **阈值** | 单一阈值 **1.25×**（超出即响亮）+ 二级 **2.0×**（判红） | 本机实测噪声上界（下表）；CV 需先量 |
| **噪声控制** | `taskset` 钉核 · 预热 · **min of N**（N≥5）· **同一门内串行**（不与其他门并行） | 全量门本身在跑别的东西 ⇒ min 是最稳的统计量 |
| **负载集** | `fib28`（纯计算最坏）+ `while_sum`（分派开销，**专盯固定开销漂移**）+ `mixed`+`jsonwb`（容器/JSON，生产形态）+ 启动 + 热构建 | 覆盖 VM/C 全谱；后四个对生产最有意义 |
| **门成本** | 目标 **≤ 90 s**（清歌的 8 负载全跑 ≈ 40 s/轨 ⇒ 只取 4 个 + 减轮数） | 全量门已 ~2 h，性能门不能成新瓶颈 |
| **豁免** | 显式豁免表（带理由 + 计数），**不允许静默跳过** | 沿用 M213/M226 纪律 |
| **判据自伤** | 负控：把阈值调到不可能满足 ⇒ 门必须判红 | 沿用 M214/M232 纪律 |

### 9.3 本机噪声量级（用于定阈值）

| 负载 | 5 轮散布（VM） | 极差/最小值 |
|---|---|---|
| `fib28` | 0.913–0.959 | **5.0%** |
| `mixed` | （见 §五 单轮） | ~5% |
| 启动 200 次 | — | ~3% |

> ⚠️ 本轮实测**是在全量门并行运行时做的** ⇒ 这 5% 是**含干扰的上界**（好消息：min 统计量对干扰不敏感）。

## 十、复现

```bash
# 0) 前置：确认产物身份（本文件的核心教训 —— 不做这步就会重犯 §四 的错）
#    C 轨产物含 fn_* 符号；VM 轨不含。示例（本机实测）：
#    C 轨  ：px build --c fib_calc.px && strings build/fib_calc | grep -c fn_fib   → 1
#    VM 轨 ：px build     fib_calc.px && strings build/fib_calc | grep -c fn_fib   → 0

# 1) M89 原版负载（§三）
cd examples/m89_perf
../..//tools/px build --c fib_calc.px && BENCH_REPS=5 taskset -c 3 ./build/fib_calc   # C 轨
../..//tools/px build     fib_calc.px && BENCH_REPS=5 taskset -c 3 ./build/fib_calc   # VM 轨

# 2) 微基准 8 负载（§五）：源码见清歌《性能基线 v2》§八（本报告附录 A 逐字收录）
for f in fib28 fib26 while_sum loop_sum mixed jsonwb textscan stridx64k; do
  mkdir -p vm_$f c_$f; cp $f.px vm_$f/; cp $f.px c_$f/
  ( cd vm_$f && ../../../tools/px build     $f.px >/dev/null )
  ( cd c_$f  && ../../../tools/px build --c $f.px >/dev/null )
done
bench() { for i in 1 2 3 4 5; do
  taskset -c 3 /usr/bin/time -f "%e" "$1" 2>&1 >/dev/null | tail -1; done | sort -n | head -1; }

# 3) px run 面（§六）
for k in 1 2 3; do /usr/bin/time -f "%e" bootstrap/pxi loop.px; done
for k in 1 2;   do /usr/bin/time -f "%e" bootstrap/pxi_vm loop.px; done
```

**本轮留证**：`/tmp/m266/`（`m1_m89.sh` 产物身份核对 · `m2_measure.sh` · `m3_micro.sh` · 各步日志）

## 十二、ONNX 内核面（M303 / S1 追加 · 2026-10-12）

### 12.1 为什么补这一节

§五 的微基准全谱是**纯语言负载**（`fib28` / `while_sum` / `mixed` / `jsonwb`）—— **一个 ONNX 项都没有**。

⇒ 在此之前，**谁把 MatMul 改快改慢，没有任何判据看得见**：M267 立的性能门看不见它，
M105 / M106 / M107 那三笔收益也全是语言侧的。
而 ONNX 执行器**就在本仓**（`runtime/onnx_*.c`），且已定为下一阶段主线（M303 §一）。
⇒ 接进账本是这条线的**第一步**（路线 S1）。

### 12.2 两个负载与实测

| 负载 | 形状 | 单次 | GFLOPS | 区间 |
|---|---|---|---|---|
| `onnx_mm512` | 512×512×512 ×5 | 0.242 s | **1.12** | 常规（数据在 cache 内） |
| `onnx_mm1024` | 1024×1024×1024 ×1 | **6.87 s** | **0.313** | **跨页崩塌** |

⚠️ **同形状的跨机对照 —— 本节最值钱的一条**：

| 机器 | 512³ | 1024³ | 崩塌倍数 |
|---|---|---|---|
| 本机 AMD EPYC 7K62 | 1.12 GFLOPS | 0.313 GFLOPS | **3.58×** |
| 观音 AMD A8-7600 | 1.12 GFLOPS | 0.085 GFLOPS | **13.2×** |

⇒ 512³ 两侧**完全一致**（1.12）· 1024³ 幅度差 3.7 倍
⇒ **形状一致、幅度随机器变** ⇒ 这是**可复现的真现象**，不是某台机器的怪癖。

### 12.3 机理：内层次长 = 恰好一个内存页

内层循环走 `k`，而 `B[k*N + j]` 的步长 = **N 个元素**：

| N | 步长 | cache line 装载率 |
|---|---|---|
| 256 | 1 KiB | 一条 line 装 4 个 |
| 512 | 2 KiB | 装 2 个 |
| **1024** | **4096 B = 恰好一页** | **每次访问都 TLB miss** |

⇒ 这与**算力无关**（单线程访存瓶颈）⇒ **加核 / 换更快的芯都不解决**。
⇒ 与 §八 的「`while_sum` 疑似固定开销漂移」是**两件事**，别混。
⇒ 对症修法是**分块 + B 预转置**（路线 S3），不是「算得更快」。

### 12.4 这不是「比 onnxruntime 快」的赛道

本节的用途是 **给 S3 立一个能判红的靶子**，不是对外宣称性能。
语言在边缘推理层的胜负手**不是"快"**（那是 kernel 工程 + 硬件）—— 是
**部署形态 / 胶水层数 / 可审计**三条。
⇒ **不该去跟 CUDA 拼算力**，也不该把「比 onnxruntime 快」当卖点（M303 §二 · §六）。

### 12.5 门的接入方式（三条可复用的决定）

| 决定 | 理由 |
|---|---|
| kind = `onnx`（**单轨**） | vm 与 c 跑的是**同一份** `onnx_exec_run` ⇒ vm/c 对照对本类负载无意义 |
| 模型**不入库** | 512³ 2 MiB / 1024³ 8 MiB；改为生成器入库、产物运行时生成到 work 目录（**刻意不缓存**） |
| 新增**下限判据** | 实测 < 基线 **0.10×** ⇒ 判红（「负载疑似未真执行」） |

⚠️ **下限判据为什么必需**：比值判据只看得见"变慢"这一侧。
缺了它，一张**坏掉的模型**（图空转 / 提前退出 / 输入为空）会以
**「性能大幅提升」** 的面目**通过**性能门 —— 那比漏报退化更危险：**它会污染 S3 的基线**。
⇒ 配套新增负控 **NC-E**（基线放大 20 倍 ⇒ 比值 <0.10 ⇒ 必须判红）证明这条判据有牙。

### 12.6 与路线图的关系（S1→S5→S2→S3→S4）

| 步 | 内容 | 状态 |
|---|---|---|
| **S1** | 性能门接 ONNX（**本节**） | ✅ 已落地（M303） |
| **S5** | 一次性基准机流程（租 → 跑 → 存 → 销毁） | ✅ **M307**（3 台一次性机档入仓：Neoverse-N2 / Xeon Gold 6462C / Xeon 6982P-C；脚本 `s5_remote_baseline.sh`） |
| **S2** | 补 `DequantizeLinear` / `QuantizeLinear` | ✅ M306（同轮补 `DynamicQuantizeLinear` / `MatMulInteger` —— 真实 int8 模型需要这三个才跑得起来） |
| **S3** | MatMul 分块 + B 预转置（**对症 12.3 的 3.58×**） | **暂缓**（2026-10-15 用户指示「机器名的事暂时不做了」）—— 前置：须先指定「在哪台机器上度量收益」（判据 = 崩塌比 ≥1.5×） |
| **S4** | RMSNorm / SiLU / GELU → KV cache / RoPE | ✅ M308（6 算子 + `Trilu` 规范名别名；**本里程碑明确定「不设绝对性能判据」** ⇒ 本节**未新增** S4 负载，性能门接入移交下一轮；口径与覆盖边界见 `docs/ONNX_INFER_OPS.md`） |

⚠️ 顺序理由（**已兑现**）：**没有基准机（S5），S2–S4 的收益都量不准** ——
这正是 S5 被排在实现类工作**之前**的原因（依据 = 本报告 §2.2 立的规矩：
**绝对值不可跨环境，但对照实验必须同机**）。S5 已于 **M307** 完成 ⇒ 后续子步度量已有同机对照档可用。

### 13.1 起因

| 时刻（UTC+8） | 事件 |
|---|---|
| 15:45:17 | 文殊系统**全量更新**（core 13 + gateways 8 + tools 全系，mtime 同一秒 ⇒ 一次整体替换） |

### 13.3 档位机制（`baselines/<cpu-signature>.tsv`）

| 规则 | 说明 |
|---|---|
| **选档** | 本机档存在 ⇒ **相对本机档**判（严格）；本机档缺失（如 CI runner）⇒ 用「各档**逐负载 max**」**合成档** |
| 合成档的语义 | 跨机绝对值本就不可比 ⇒ 上限判据自动宽松，**但下限判据（<0.10×）不变**（仍能抓「负载没真跑」） |
| 签名单一实现 | `examples/m267_perf/machine_sig.sh`（`verify.sh` 与 `check_spec_consistency.sh` **共用**） |
| **环境随档** | 档头注自带 `machine-sig` / `生成机` / `工具链`；SPEC **不再**断言「实机必须匹配某固定 CPU/px 版本」 |
| 建本机档 | `bash examples/m267_perf/verify.sh --update` |
| 列档 | `bash examples/m267_perf/verify.sh --baselines` |

**为什么不做「按机器硬写死」**：那会让换机 = 改代码。
**为什么不做「只留一份最新档」**：那会**永久丢掉跨机对照** —— 而本次对照恰好产出了 §13.4 的结论。
**为什么把「环境声明」从 SPEC 挪进档文件**：`env_px=0.2.17` 这类断言自 M271 起就与实机脱节 ⇒ 写死在口径里只会变成「每轮必红的假红源」。

### 13.4 ⭐ 对路线图的影响：S3 的靶子在 Xeon 上小了一大半

§12.3 把 `onnx_mm1024` 的「跨页 TLB 崩塌」（内层次长 = N 个元素；N=1024 时 **4096 B = 恰好一页**）定为 **S3（MatMul 分块 + B 预转置）的靶子**。

| 机器 | 512³ GFLOPS | 1024³ GFLOPS | 崩塌比（512 ÷ 1024） |
|---|---|---|---|
| EPYC 7K62 | 1.103 | 0.294 | **3.75×** |
| **Xeon E5-2682 v4** | 0.649 | 0.483 | **1.34×** |

⇒ **崩塌在这台机器上几乎消失** ⇒ 该现象**很可能是 EPYC 的架构特性**（分片 L3 / TLB 行为），不是通用规律。
⇒ **S3 的收益预期必须下调**，且以后提 S3 时必须**指定机器**。
这正是 §2.2 那条规矩（「绝对值不可跨环境」）的**实例**：我们是靠**保留第二档**才看得见它的。

## 十四、S5「一次性基准机」+ **aarch64 第一档**（M307 · 2026-10-13）

### 14.1 起因：S5 从「暂缓」到「落地」

§十三 的结论是「**绝对值不可跨机**，所以门改成每机一档」。但那只解决了一半 ——
**档从哪来**仍靠人手（ssh 上去、下包、装依赖、跑采集、拷回来），而 **dongyue 自己不能当基准机**：

| 理由 | 依据 |
|---|---|
| 它**既跑生产又跑门** | 负载会抖 —— M305 那次冷迁移本身就是活例 |
| 它**不是我们控制的机器** | 云厂商可随时把实例冷迁到另一颗 CPU（2026-10-12 真发生过：EPYC 7K62 → Xeon E5-2682 v4） |
| 基准要求**干净** | 采集口径 §3.1 明确「尽量无干扰」 |

⇒ 正解 = **租一台干净的机器 → 跑基线 → 档存回仓库 → 销毁实例**（路线图 S5）。
本轮把它做成一条命令：`examples/m267_perf/s5_remote_baseline.sh`。

### 14.2 本轮采的机器（唯一一台 · 一次性 · 已销毁）

| 项 | 值 |
|---|---|
| 云 / 规格 | 阿里云 **8 vCPU / 16 GiB · 计算型 c8y**（**独享** · `steal = 0` —— 基准机的全部意义就在这） |
| CPU | **ARM Neoverse-N2**（倚天 710）· 单插槽单 NUMA · 3.0 GHz · L3 64 MiB · 带 `sve2 / svei8mm / svebf16` |
| OS / 工具链 | Rocky Linux 9.8 · gcc 11.5.0 · px 0.2.281（与仓库当前一致） |
| 盘 | 100 G NVMe（实测顺序写 151 / 读 131 MB/s） |
| 落包校验 | aarch64 引导包 `v0.2.306` sha256 `9ba664fa…98ebe` 与发布方 `.sha256` **逐字符一致** |
| 采集质量 | **3 组独立采集** · **最大偏差 1.97%**（容差 run/startup 10% · build 15%） |

⚠️ **为什么特意选 ARM**：本仓验证矩阵里 **「aarch64 × el9」这一格此前从未真机验过** ——
aarch64 只在 openEuler 上跑过，el9 只在 x86_64 上跑过。这台机器正好补这一格（下一轮起它就是基线机候选）。

| while_sum_c | 0.065 | 0.1031 | **0.0381** | 0.59 | 0.37 |
| mixed_vm | 0.4957 | 0.9673 | **0.3497** | 0.71 | 0.36 |
| mixed_c | 0.4984 | 0.9554 | **0.3422** | 0.69 | 0.36 |
| jsonwb_vm | 1.4235 | 3.0583 | **1.5774** | **1.11** | 0.52 |
| jsonwb_c | 1.416 | 3.1418 | **1.5903** | **1.12** | 0.51 |
| startup_exec | 0.001463 | 0.003342 | **0.001581** | **1.08** | 0.47 |
| hot_build | 0.4646 | 1.0572 | **0.373** | 0.80 | 0.35 |

**两条值得单说**：
- N2 对 Xeon **全面快 1.7–2.9×**（N2 是 2021 年 ARM 核，Xeon E5-2682 v4 是 2016 年 x86 核）。
- 但 **`jsonwb_*` 与 `startup_exec` 在 N2 上反而比 EPYC 慢 8–12%**（内存/缓存敏感 + 进程启动）
  —— 与 §13.2「慢得不均匀正是特征」同向：**不同微架构的短板不同**，这正是「单机档」存在的理由。

但**纯计算**负载上 N2 的比值更高（`while_sum` **6.94×** ≫ EPYC 5.11× / Xeon 4.61×）
⇒ 解释器循环在 N2 上**相对**更贵（分派 / 间接跳转的微架构差异）。**如实登记，本轮不追。**

### 14.4 ⭐ 崩塌比的第三个数据点：N2 上**它不存在**

§12.3 把 `onnx_mm1024` 的「跨页 TLB 崩塌」（内层次长 = N 元素；N=1024 时 **4096 B 恰一页**）
定为 **S3（MatMul 分块 + B 预转置）的靶子**；§13.4 发现 Xeon 上只有 1.34×（EPYC 3.75×）⇒ 已下调过一次。

| 机器 | 512³ GFLOPS | 1024³ GFLOPS | **崩塌比**（512 ÷ 1024） |
|---|---|---|---|
| AMD EPYC 7K62 | 1.103 | 0.294 | **3.75×** |
| Intel Xeon E5-2682 v4 | 0.649 | 0.483 | **1.34×** |
| **ARM Neoverse-N2** | **1.437** | **1.442** | **≈1.00×（零崩塌）** |

⇒ 三档 **3.75× / 1.34× / 1.00×** 单调递减，与 §13.4 的推断（「该现象很可能是 **EPYC 的架构特性**」）一致；
⇒ **S3 的收益预期再次下调**，且在 N2 上**它根本没有靶子** ⇒ 以后提 S3 **必须指定机器**；
⇒ 顺带：N2 的绝对算力也最高（512³ **1.437** GFLOPS，比 EPYC 档高 **30%**）。

### 14.5 流程（`examples/m267_perf/s5_remote_baseline.sh`）

一条命令：**落包 → 装依赖 →（aarch64）自举 VM 件 → 3 组采集 → 回传 → 固化 → ONNX 补测 → 自校验**。
每步都有判据（sha256 强校验 · 静态链接自证 · 远端仓库根现场求值 · 档不存在才写 · 汇总带跨机对照）。

**三条实测得出的设计**（每条都是踩过才写下来的）：

1. **落包走国内镜像**（`soft.xiusoft.cn` 0.06 s 响应 ⇄ GitHub 资产仅 ~0.87 MB/s）+ sha256 与 `version.json` 对拍。
2. **aarch64 官方引导包不含 VM 轨件**（`build_native_tools.sh` 主动移除 —— 非 x86_64 包内带 VM 件

### 14.6 顺带收口的三处缺陷（**只在非 x86 上显形**）

| # | 位置 | 症状（aarch64 实测） |
|---|---|---|
| **531** | `machine_sig.sh` · `collect_baseline_v2.sh` · `check_spec_consistency.sh` · `verify.sh --update`（**四处同源**）都只读 `/proc/cpuinfo` 的 `model name`，而 **aarch64 没有这个字段**（ARM 用 `CPU implementer` / `CPU part`，如 `0x41` / `0xd49` = Neoverse-N2） | 签名退化成 `unknown-aarch64` ⇒ **所有 ARM 机型共用一个档**（档机制对 ARM 失效）；档头注「生成机」缺型号；`check_spec_consistency` 在 aarch64 上对本机档**判红** |
| **532** | `freeze_baseline_v2.py` **不写** `# machine-sig:` | 档建出来**门当场判红**（`❌ 选定档头注既无 machine-sig 也不是合成档`）—— M305 时 Xeon 档靠**手工补**才过的 |
| **533** | `collect_baseline_v2.sh` 的 `GATES0=$(pgrep -fc … \|\| echo 0)` | `pgrep -fc` **无匹配时本就打印 0**（rc=1）⇒ 得 `"0\n0"` ⇒ 命令替换成 `"0 0" ≠ "0"` ⇒ **`quiet` 恒判 false**、报告恒写「采集窗口存在并发全量门」= **假陈述**（M223 已收录同款形状，这是第 2 次） |

**收口**：把「取 CPU 型号」抽成 **`machine_model()`**（与 `machine_sig()` 同在 `machine_sig.sh`，
**单一实现**；x86 路径一字未动：先取 `model name`，取不到才回退 `lscpu` 的 `Model name:`），
四个站点全部改调它；`freeze` 新增 `--machine-sig`；`quiet` 判据改 `| head -1`。
**全仓普查**：`grep -rn /proc/cpuinfo` 现仅剩 `machine_sig.sh` 一处（带 aarch64 回退）。

### 14.7 边界（如实登记）

- **S5 只管「跑 + 存」** —— 「租」与「销毁」是云 API/控制台的事（本轮由用户手工开/关）。
- 采集机**已销毁** ⇒ 档中 VM 轨数字来自**本机自举**的 VM 编译器
  （同一 `compiler.px` + 同一 `runtime/vm.c`，语义相同）；档头注已标注该来历。
- `jsonwb` / `startup_exec` 在 N2 上比 EPYC 慢 **未追根因**（本轮目标是「把档建出来 + 把流程做出来」）。
- **ONNX 两项不在 `collect_baseline_v2.sh` 的 LOADS 里**（采集器口径如此）⇒ 由 `s5_remote_baseline.sh`
  第 6 步单独补测后追加，与 M303 建 EPYC 档同做法。若日后要把 onnx 纳入采集器，
  需同时改 `collect_baseline_v2.sh` / `baseline_v2_json.py` / `freeze_baseline_v2.py` **三处**的 ORDER
  （注意：改 ORDER 会让**旧 raw** 在 `compare` 时报「有采集缺此指标」⇒ 需同步重采或兼容处理）。
- 本档是**第三档**，也是**第一台 aarch64 档**；合成档机制（无本机档时取各档逐负载 max）未改。
