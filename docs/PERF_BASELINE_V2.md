## 三、M89 原版负载复跑（`examples/m89_perf/fib_calc.px`，`BENCH_REPS=5`）

md5 `4085d090734ff84bc0f08ab9773fd3aa`（与清歌所报逐字节一致）。

| 轨 | M89 记录（2026-09-09 · px 0.2.0） | 清歌（2026-10-05 · 0.2.9-m259） | **本机（2026-10-05 · 0.2.17）** | 本机相对 M89 |
|---|---|---|---|---|
| **C 轨** | 6.091 s | 0.28 s | **0.246 s**（5 轮 0.256/0.252/0.247/0.246/0.247） | **24.8× 提速** |
| **VM 轨** | 9.283 s | 1.21 s | **0.913 s**（5 轮 0.920/0.915/0.959/0.940/0.913） | **10.2× 提速** |
| **VM/C** | **1.52×** | 4.32× | **3.71×** | 比值**被拉大 2.4×** |

**✅ 清歌的量级确认**（其报 21.8×/7.7×，本机 24.8×/10.2×；同机同型号 CPU，差值 10–25% 属版本/频率档差异）。

**归因复核（清歌的推断）**：
```c
// C 轨产物 fib_calc.c（本机实查）
return px_call(px_get_global("fib"), …);      // 每次递归 = 一次全局名解析
```
M105-S2 把 `px_get_global` 从"线性 `strcmp` 扫描（平均 331.6 项探测）"改为 **O(1) 哈希表**
（`strcmp` −99.6%）—— **两轨都在付这笔钱，C 轨调用更密、付得更多** ⇒ 绝对提速更大、比值反而拉开。
**结论：清歌的归因成立。**

## 四、⭐ 新发现：**基线生成器自己已经失真**（本轮最重要的结构性发现）

`examples/m89_perf/bench_vm_vs_c.sh`（M89 写的"默认轨切换决策数据"生成器）里这两行：

```bash
"$PX" build     fib_calc.px   && cp build/fib_calc "$BIN/fib_calc_c"     # 标签 c
"$PX" build --vm fib_calc.px  && cp build/fib_calc "$BIN/fib_calc_vm"    # 标签 vm
```

**M91 把 `px build` 的默认轨从 C 切成了 VM**，而 `--vm` 成了**同义冗余 flag**（`tools/px:107` 明确写着
"VM 轨（M91 起 = 默认，flag 保留兼容）"）⇒ **两条命令产出的都是 VM 轨**。

实测（本机，同机器同轮）：

| 脚本里的标签 | 实际命令 | `fn_fib` 符号 | 5 轮 min |
|---|---|---|---|
| `fib_calc_c`（"C 轨"） | `px build` | **0**（= VM 轨） | 0.951 s |
| `fib_calc_vm`（"VM 轨"） | `px build --vm` | **0**（= VM 轨） | 0.958 s |

⇒ 该脚本现在测的是 **VM vs VM（1.007×）** —— 它**既测不出 1.52×，也测不出 3.71×**。

**为什么没人发现**：`grep -rn m89_perf` 在 `selfhost/gates.registry.sh`、`.github/workflows/ci.yml`
与全部 `examples/*/verify.sh` 里 **0 命中** ⇒ **这份"决策数据底座"的生产脚本从未被任何门跑过**。

> 📌 这是本仓同一形状的**第 N 次**（M251 孤儿门、M259 本地≠CI、M223 选料不可判定）：
> **没有判据的自动化 = 迟早静默腐烂，且腐烂时无人知晓。**
> 与清歌 §2.5 的判断合起来看：**过期基线比没有基线更危险** —— 现在还要加一句：
> **产生基线的脚本本身也会过期，而且它比数字更隐蔽。**

**处置**：本轮回修脚本（`--vm` → `--c`，并加产物判别自检）；并在 §九 把它纳入性能门。

## 五、微基准全谱（本机 v2 基线 · 8 负载 × 双轨）

方法同 §2.3。**这是本机第一组、可被性能门直接引用的数字。**

| # | 负载 | 形状 | VM (s) | C (s) | **VM/C** | 清歌 VM/C | stdout 一致 |
|---|---|---|---|---|---|---|---|
| 1 | `fib28`（×5 递归） | 纯递归 | 0.961 | 0.264 | **3.64×** | 4.11× | ✅ |
| 2 | `fib26`（×5） | 纯递归 | 0.374 | 0.103 | **3.63×** | 4.50× | ✅ |
| 3 | `while_sum` 3M | 算术/比较/JMP | 0.333 | 0.064 | **5.20×** | 6.67× | ✅ |
| 4 | `loop_sum` 3M（`range` 物化） | 迭代 + 物化 | 0.298 | 0.113 | **2.64×** | 2.54× | ✅ |
| 5 | `mixed` 20 万（dict+list+str） | 容器 | 0.505 | 0.524 | **0.96×** | 0.97× | ✅ |
| 6 | `jsonwb` 2 万对象 构→串→解 | JSON | 1.380 | 1.440 | **0.96×** | 1.01× | ✅ |
| 7 | `textscan` 3 万行 split+contains+regex | 文本 | 0.067 | 0.076 | **0.88×** | 0.76× | ✅ |
| 8 | `stridx64k` 65 540 字符逐字符索引 | M106 场景 | 0.228 | 0.242 | **0.94×** | 0.96× | ✅ |

**启动**：空程序 200 次连跑 = 0.305 s ⇒ **1.53 ms/次**（清歌 2.30 ms）。
**热构建**：0.54 s（清歌 0.76 s）。冷构建本轮未测（会打断并行全量门的缓存，见 §十）。

### 读法（决定"要不要走 `--c`"的唯一依据）

```
纯计算 / 深递归  →  VM 慢 2.6–5.2×   ⇒ 用 --c 有意义
容器 / JSON / 文本 / 大串  →  VM/C = 0.88–0.96×  ⇒ **C 轨不更快，甚至更慢**
```

⇒ 与 M104"成本主体是**动态值层**而非分派层"的结论**一致**：
纯计算把"值层开销"摊在算术上所以差距大；容器/字符串负载**本身就活在值层里**，两轨拉不开。

> ⚠️ **因此 `--c` 的正确说法是**："纯计算热点约 **3.6×**（不是 1.5×）；容器/文本负载**无收益**。"
> 现值 `tools/px:113` 写"纯计算热点程序用 ≈ 1.5x 性能" —— **两个方向都错**（幅度低估、
> 且没提"多数负载无收益"）。本轮修正。

## 七、字符串 `+=` 是 O(n²)（运行时层 · 三轨同病）

本机复跑（VM 轨产物，3 轮取 min）：

| n | `s += "x"` | `list.append` + `join` | 差距 | 晨曦数据（`+=`） |
|---|---|---|---|---|
| 7 500 | 25.9 ms | 4.7 ms | 5.5× | 33 ms |
| 15 000 | 81.2 ms | 6.2 ms | 13× | 99 ms |
| 30 000 | 463.6 ms | 8.5 ms | 55× | 616 ms |
| 60 000 | **1 950 ms** | 13.8 ms | **141×** | 2 937 ms |

**n 翻倍 ⇒ 耗时 ≈ 3.1× / 5.7× / 4.2× ⇒ 确证 O(n²)**（`append+join` 侧 4.7→6.2→8.5→13.8 = 线性）。
**✅ 晨曦数据逐点同量级确认。**

**性质**：这是**运行时层**（`px_str_concat` 每次分配新缓冲并整体复制），**三条轨都受影响** ——
不是解释器的问题，也不是 VM 的问题。⇒ 单独立项（M270）。

## 九、性能回归门的设计（供 M267 立项）

### 9.1 为什么必须要门

- 全仓 **179 个门全是正确性门**（`grep -c '^run ' selfhost/gates.registry.sh` = 179；无一性能判据）。
- M105/M106/M107 的三笔收益（1.88× / 1.78× / 5.6×）**全靠人工量化** ⇒ 后续任何重构都可能悄悄退回去。
- 本轮实证：连**生成基线的脚本**都烂了 8 个月（§四）而无人知晓。

### 9.2 门的设计要点（按"避免假阳/假阴"取舍）

| 要点 | 做法 | 理由 |
|---|---|---|
| **判据形态** | 报**相对基线的 ×倍**，不报绝对秒 | 机器/负载会变，绝对值不可跨环境 |
| **阈值** | 单一阈值 **1.25×**（超出即响亮）+ 二级 **2.0×**（判红） | 本机实测噪声上界（下表）；CV 需先量 |
| **噪声控制** | `taskset` 钉核 · 预热 · **min of N**（N≥5）· **同一门内串行**（不与其他门并行） | 全量门本身在跑别的东西 ⇒ min 是最稳的统计量 |
| **负载集** | `fib28`（纯计算最坏）+ `while_sum`（分派开销，**专盯固定开销漂移**）+ `mixed`+`jsonwb`（容器/JSON，生产形态）+ 启动 + 热构建 | 覆盖 VM/C 全谱；后四个对生产最有意义 |
| **门成本** | 目标 **≤ 90 s**（清歌的 8 负载全跑 ≈ 40 s/轨 ⇒ 只取 4 个 + 减轮数） | 全量门已 ~2 h，性能门不能成新瓶颈 |
| **豁免** | 显式豁免表（带理由 + 计数），**不允许静默跳过** | 沿用 M213/M226 纪律 |
| **判据自伤** | 负控：把阈值调到不可能满足 ⇒ 门必须判红 | 沿用 M214/M232 纪律 |

### 9.3 本机噪声量级（用于定阈值）

| 负载 | 5 轮散布（VM） | 极差/最小值 |
|---|---|---|
| `fib28` | 0.913–0.959 | **5.0%** |
| `mixed` | （见 §五 单轮） | ~5% |
| 启动 200 次 | — | ~3% |

> ⚠️ 本轮实测**是在全量门并行运行时做的** ⇒ 这 5% 是**含干扰的上界**（好消息：min 统计量对干扰不敏感）。

## 十、复现

```bash
# 0) 前置：确认产物身份（本文件的核心教训 —— 不做这步就会重犯 §四 的错）
#    C 轨产物含 fn_* 符号；VM 轨不含。示例（本机实测）：
#    C 轨  ：px build --c fib_calc.px && strings build/fib_calc | grep -c fn_fib   → 1
#    VM 轨 ：px build     fib_calc.px && strings build/fib_calc | grep -c fn_fib   → 0

# 1) M89 原版负载（§三）
cd examples/m89_perf
../..//tools/px build --c fib_calc.px && BENCH_REPS=5 taskset -c 3 ./build/fib_calc   # C 轨
../..//tools/px build     fib_calc.px && BENCH_REPS=5 taskset -c 3 ./build/fib_calc   # VM 轨

# 2) 微基准 8 负载（§五）：源码见清歌《性能基线 v2》§八（本报告附录 A 逐字收录）
for f in fib28 fib26 while_sum loop_sum mixed jsonwb textscan stridx64k; do
  mkdir -p vm_$f c_$f; cp $f.px vm_$f/; cp $f.px c_$f/
  ( cd vm_$f && ../../../tools/px build     $f.px >/dev/null )
  ( cd c_$f  && ../../../tools/px build --c $f.px >/dev/null )
done
bench() { for i in 1 2 3 4 5; do
  taskset -c 3 /usr/bin/time -f "%e" "$1" 2>&1 >/dev/null | tail -1; done | sort -n | head -1; }

# 3) px run 面（§六）
for k in 1 2 3; do /usr/bin/time -f "%e" bootstrap/pxi loop.px; done
for k in 1 2;   do /usr/bin/time -f "%e" bootstrap/pxi_vm loop.px; done
```

**本轮留证**：`/tmp/m266/`（`m1_m89.sh` 产物身份核对 · `m2_measure.sh` · `m3_micro.sh` · 各步日志）

## 十一、边界（如实登记 · 本轮做了什么、没做什么）

产物身份双侧核对 · 基线生成器自检 · 与清歌/晨曦逐项对账。

**没做 / 未定论**：

| 项 | 原因 |
|---|---|
| **冷构建耗时**（清歌 19.02 s） | 清 `.rtcache` 会打断**并行运行中的全量门**（179 门，33% 进度）⇒ 本轮未测，M267 补 |
