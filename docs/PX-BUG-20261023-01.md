## 1 现象

对端「TCP 已连上，但一个字节都不发」时，`ws_connect()` 永久阻塞：

- 调用线程被永久占住（服务端 worker 池被一条条吃光）；
- 连接**不进会话表**（槽位分配发生在握手**之后**）⇒ 用 `ws_sessions()` 看不到，运维人员
  「明明连接数在涨，会话数不涨」；
- **不打日志**（失败出口在握手返回之后才走到）；
- **fd 不释放**；
- 只能重启进程回收。

广州现场（报障方提供）：积压 **21 条**握手挂死连接，**会话数:连接数 = 28:1**。

## 2 根因（两处，各自独立生效）

```
① 建链：connect() 裸阻塞
   runtime/runtime_ws.c 四处（URL 明文 / (host,port,path) / ws_connect_auto / 自动重连）
   对 SYN 被丢弃的对端，等的是内核重传超时（实测 >45s，某些路径无上界）。

② 握手：读响应头无超时
   ws_client_handshake_px → ws_read_http_header → px_conn_read → recv()
   px_conn_read_body 的明文分支只处理 EINTR（M211 缺陷 265 的修复），
   EAGAIN 直接返回 -1 —— 但**客户端 fd 从来没设过 SO_RCVTIMEO**，
   所以根本不会产生 EAGAIN，只会在 recv 上无限阻塞。
```

> 注：服务端 `ws_serve` 的 accept 后握手是**另一个**攻击面（「被连方」的慢速连接），
> 不在本缺陷范围，已登记待办。

## 3 修法（两条边界，互不掩盖）

```
① 建链有界
   ws_connect_bounded()：fcntl(O_NONBLOCK) → connect → poll(POLLOUT, timeout)
   → getsockopt(SO_ERROR) 复核 → fcntl 恢复阻塞。
   到点返回 -1/ETIMEDOUT；`EINPROGRESS` 与 `EINTR` 各自正确处置（后者重试）。
   四条建链路径全部改走它 —— 解析入口仍只有 px_ws_resolve_v4 一处（M240/M255 契约不变）。

② 握手有界
   ws_client_handshake_bounded()：握手前给 fd 设 SO_RCVTIMEO/SO_SNDTIMEO，
   握手完成后**无条件清零**。
   ⚠️ 清零是这条修复的**另一半**：漏了就把「防挂死」变成「5s 后静默丢帧」——
      那是比原缺陷更难发现的形态（正常业务里 5s 无数据的连接并不罕见）。
      门里为此专设判据 flow:7（握手后 7s 才来的首帧必须收到）。
```

默认值与旋钮：

| 旋钮 | 默认 | 说明 |
|---|---|---|
| `PX_WS_CONNECT_TIMEOUT_MS` | 10000 | 建链上限 |
| `PX_WS_HANDSHAKE_TIMEOUT_MS` | 5000 | 握手（写请求 + 读响应头）上限 |

取值 ≤0 或非法 ⇒ 回落默认。**不提供「0 = 无限」**：那等于给这条缺陷留一个后门。
上限钳制 120000ms。

## 4 未覆盖边界（明确登记，不装作已解决）

1. **`wss://` 的 TLS 握手与读响应头**。BIO 是 `mbedtls_net_recv`（非 timeout 版），
   给同一 fd 设 `SO_RCVTIMEO` 会与 mbedtls 的 `read_timeout` 语义打架
   （见 `runtime/runtime.c` M150 注释）。要修必须改 BIO 为 `mbedtls_net_recv_timeout`
   并统一 read_timeout 口径 —— 影响所有 HTTPS 客户端，独立任务。
2. **服务端 `ws_serve` 的 accept 后握手**：同样的「连上不说话」可占满 worker。
   修法与客户端不同（服务端应设 idle timeout 而非一次性握手超时），独立任务。

## 5 判据（门 m375 · 26 条断言）

| 层 | 判据 | 为什么需要它 |
|---|---|---|
| 静态 8 | 4 条建链路径全走 helper · 裸 connect 清零 · 握手 5 处全走 bounded · **清零契约在场** · 默认值与上界 · 缺陷号可追溯 · SO_ERROR 复核 | 防「只改了看得见的那一条路径」 |
| 正控 | now（立即 101）⇒ ok 且 < 3s | 防修复把正常握手一起打死 |
| 延迟分辨 | delay:2 ⇒ ok · delay:8 ⇒ null | 把超时值锚在契约区间，而不是「随便返回 null」 |
| **主判据** | never ⇒ null **且 rc≠124** 且 4.5~9s | rc=124 = 外壳 timeout 杀的 = 内部没超时。这一条把「假绿」挡在门外 |
| 边界 | flow:7 首帧必须收到 | 防「超时漏到正常收发」（本修复的另一半） |
| 第二路径 | ws:// URL 形式 + never ⇒ null | URL 分支是另一段建链代码 |
| 邻居 | refuse ⇒ null 且 < 2s | 「快速失败」与「超时」是两条路径，都不能丢 |
| 负控 A/B | HS=1200 时 delay:2 翻转 null；HS=12000 时 delay:8 翻转 ok | 证明判据的自变量**确实是超时值**，不是恒真/恒假 |

修前实证（同一夹具、同一探针，`bootstrap/pxi` = 改动前入库件）：

```
never 模式   修前 rc=124（外壳 20s 强杀，进程从未返回）  →  修后 rc=0，5506ms 返回 null
```
