# `px run --fast` —— 用户脚本构建缓存（M268 口径）

> 一句话：**`px run --fast` 让「同一脚本反复运行」从 11.6 s 掉到 ~30 ms（实测 370×），
> 而**默认 `px run` 一个字节都不变**。**

---

## 一 为什么会有这一项

来历：晨曦《px run（解释轨）性能：量化 · 根因 · 三个方向》（2026-10-05）。
本机复跑复核（M266，`docs/PERF_BASELINE_V2.md` §六）：

| 引擎 | 本机（px 0.2.17） | 相对 |
|---|---|---|
| `bootstrap/pxi`（tree-walking 解释轨） | **11.6 s** | 1× |
| `bootstrap/pxi_vm`（**解释器自身**编到字节码轨） | 7.6 s | 1.53× |
| `px build` 产物（默认 VM 轨） | **30.7 ms** | **378×** |
| `python3` 3.9 | 28.9 ms | 402× |
| `px run` 启动（`tiny.px`） | 4.7 ms | — |

四条轨 stdout 逐字节一致。⇒ 慢的不是 PuXian，是 `px run` 那一层**逐节点求值**的解释器。
M111 自己早已把这条写清：「残余 = 解释器逐节点求值的**固有开销**（与串长无关）」，
且 M71-S5 / ECOSYSTEM_GAPS F4 的既有口径就是「真重负载走 `px build` 产物」。

⇒ `--fast` = **把那条口径自动化**：不用手写 `px build` + 找产物路径，命令层面直接给。

---

## 二 为什么**默认关**（这是本节最值得记的一条）

`px run` 的**秒起（4.7 ms）不是体验问题，是基础设施属性**：

| 依赖方 | 数量 |
|---|---|
| 门脚本里调 `px run` | **20 个** |
| 直接调 `bootstrap/pxi` | **66 个** |

默认加编译 ⇒ **每个调用点 +0.5–1 s** ⇒ 全仓 CI 被拉长（全量门已 ~2 小时）。
⇒ 结论：**显式开**。收益不打折 —— 重计算脚本改写 `px run --fast`（或 `px build`）即可。

---

## 三 ⚠️ 语义口径：**缓存只许影响快慢，不许影响语义**

`px run` 的现契约是 **Mini 子集**（`docs/MINI_SUBSET.md` §边界表）：
并发原语（`spawn` / `chan` / `chan_try_recv` / `select_try` / `mutex` / `rwlock`）
**只有编译轨支持**，解释轨响亮拒绝。

若「缓存命中 ⇒ 直接 exec 编译产物」，则**「这脚本能不能 `spawn`」会变成由「有没有开 `--fast`」决定**
—— 那是**缓存改变语义**，不可接受。缓存的语义必须**只由源码决定**。

⇒ 实现带**子集守卫**（`run_subset_ok`）：

```
px run --fast <脚本>
   │
   ├─ 缓存命中 ─────────────────────────────► exec 产物（~5 ms）
   │
   └─ 未命中
        ├─ 子集守卫：脚本含并发构造？ ──► 是 ⇒ 打印提示 + **回落解释轨**（行为与默认 100% 一致）
        │
        └─ 否 ⇒ px build（~1 s）→ 入缓存 → exec
```

**守卫判据形态**：解析出的 **AST**（`bootstrap/pxpar`），**不是源码文本** ⇒
不误命中注释与字符串字面量。
**方向：过近似** —— 假阳性只损失速度，不损失正确性。

实测（本机）：

| 脚本 | `--fast` 行为 | 与默认档对比 |
|---|---|---|
| `spawn work()` | 提示「并发语句(spawn/chan/send/recv/select)」⇒ 回落解释轨 | 报**同一个** `R1002 interp 不支持 spawn（Mini 子集排除）` |
| `var m = mutex()` | 提示「并发 native(mutex)」⇒ 回落解释轨 | 同上（`interp 不支持 mutex`） |
| 纯计算 20 000 次循环 | 编译 + 缓存；二次运行 **0.005 s** | 解释轨 **1.91 s**（**370×**） |

## 四 缓存 key（**必须含脚本内容**）

```
key = sha256( 脚本文本 sha256
            | px --version
            | px rtkey "" gcc 0          ← runtime 源内容哈希（**不编译**，0.16 s）
            | bootstrap/pxc_vm sha256
            | PX_BUILD_ENGINE ) | cut -c1-16
```

三条设计理由：

1. **必须含脚本内容** —— `.rtcache` 的 key **不含**脚本内容，那是**对的**
   （它是 runtime 的对象缓存，且按"引用集 cuts"分桶）；这里若不含，
   **改了脚本还命中旧产物 = 错误的缓存**。（晨曦实测的边界二也是这条：
   `.rtcache` 的触发条件是「引用集变了」而不是「脚本改了」。）
2. **全部用内容/版本信号，不用 mtime** —— M169 缺陷 185 / M223 缺陷 323 的教训：
   「能自动挑选的东西，也要能自动核对挑对没有」；mtime 会因 `touch`/`cp`/解包而漂移。
3. **含 runtime 源内容** ⇒ runtime 一变，**全部缓存失效**（保守但正确）。
   ⚠️ 副作用（**实测**）：运行中的全量门会**临时改 `runtime/*.c`**（负控打桩）
   ⇒ 那段时间里 rtkey 每几分钟就变 ⇒ `--fast` 会连续多次 miss。
   这是**正确**行为（内容哈希必然如此），不是缺陷 —— 但它意味着
   **在门运行期间做 `--fast` 性能测试，数据不可信**。

缓存落点：`$PXC_HOME/.runcache/<key>/prog`（与 `.rtcache` 同源策略，已进 `.gitignore`），
可用 `PX_RUNCACHE_DIR` 覆盖；`PX_RUN_NOCACHE=1` 全局关。

## 五 契约

| 命令 | 行为 |
|---|---|
| `px run x.px [args...]` | **完全不变**（解释轨；脚本自动置于末位，前置参数按数据文件透传） |
| `px run --interp x.px` | 显式强制解释轨（同默认；与 `--fast` 成对，便于脚本自述） |
| `px run --fast x.px [args...]` | 编译缓存路径；子集外脚本**自动回落**且行为不变 |

环境变量：`PX_RUNCACHE_DIR`（缓存根）· `PX_RUN_NOCACHE=1`（禁用 `--fast`，等价 `--interp`）。

---

## 六 覆盖边界（如实登记）

- **`--fast` 只对「Mini 子集内」的脚本生效**。「升级 `px run` 为全语言运行器」是**独立的契约变更**
  （要改 `MINI_SUBSET` + `diffcheck` 的 run 层 + `engine_parity` + 所有依赖"子集拒绝"的判据），
  未在本轮做。需要全能力 ⇒ 用 `px build`（M71-S5 的既有结论）。
- 首次运行要付编译成本（热 ~1 s / 冷 ~20 s）⇒ 对「跑一次就丢」的短脚本是**负优化**；
  这正是默认关的理由。
- `--fast` 下的 `args()` 语义：编译产物收到的是**用户参数**（脚本路径不入 argv）。
  解释轨受 `pxi` 约定所限，argv **末位是脚本路径** ⇒ 两侧对 `args()` 的观察**不同**。
  ⚠️ **本项未单独建门**（登记为下一轮候选）：写 `args()` 的脚本在两种模式下会看到不同内容。
- 缓存**不做过期淘汰**（与 `.rtcache` 同）：长期使用会累积；`rm -rf .runcache` 即净。
- 本轮**未做**：把 `--fast` 纳入 CI 性能门（M267 的门只覆盖 `px build` 两侧；
  `px run` 面登记为下一轮候选）。

⚠️ **「子集外 ⇒ 回落解释轨」是设计，不是缺陷** —— 子集外脚本的唯一出路是解释轨，
所以那条回落**保留**（且必带响亮提示）。被禁止的是「**在子集内、编译本应成功**时回落」——
那会把「编译器故障」静默成「慢但正确」。

⚠️ **缺陷 469**：`cmd_run_fast` 的 `shift` 之后，`"$@"` **不含脚本路径** ⇒
两处 `"$PXI_BIN" "$@"` 会让解释轨拿到「脚本的参数」。已修（两处补 `"$file"`）+ 判据 `[1.6]`。
