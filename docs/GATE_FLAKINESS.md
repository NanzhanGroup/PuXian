# 判据不稳定性台账（GATE_FLAKINESS）· 2026-10-27 建立（M340）

> 为什么要这份台账：**2026-10-26 22:43 → 10-27 13:45 我跑了 7 次全量门，只有 1 次全绿**。
> 每次红都换一个门，而同树单跑必绿 ⇒ 「全量门绿」已经不能当信号用。
> 这比单个门红严重：它会训练人「红 = 又抽中了」—— 而「假红让真红不再被相信」正是缺陷 584 开头写下的失效模式。

## 二 从这 6 条抽出的四条口径（可直接当 review checklist）

1. **观测窗口 ≥ 现象的随机性**：时间窗口/CPU ticks 类判据必须多轮取样，任一命中即判红；
   不要用「单轮结果」下「判据没有牙」这种结论。
2. **就绪判据必须等于被测通道**：日志打印 READY ≠ 端口可连；两者要分别自证（m150）。
3. **同一门里对同一事实只读一次**：静态断言读一次快照，别反复 `cat` 工作树（m278）。
4. **前提断言先于症状断言**：注入类负控先断言「注入装上了 / 命中了」，再断言症状（m128 的 `/arm` + `注入命中`）。

### 二·补 M341 修正：上面四条**不够**，真正的两轴是这两条（缺陷 597）

M340 时我写的是「主要风险面在时间量判据」。M341 实测 216 个已注册门后，这条被自己的数字推翻：
**6 个已定性案例里只有 1 个（594）涉及时间量**，其余 5 个的病根是「单次取样」或「判据通道 ≠ 被测通道」。
⇒ 台账从「按时间量过滤」改成**两轴过滤**，请按这两条 review，不要按时间量找：

5. **取样次数 ≥ 现象的随机性**：现象本身是概率性的（并发 / 竞态 / 信号 / EOF 时机 / 调度 / 隔离），
   **一次观测就下结论 = 判据在上报「这次没抽中」**。判定口径优先用「N 轮内任一命中即判红」，
   并把每轮数值打出来；「重试到绿」是掩盖，不是处置。
6. **判据通道 = 被测通道**：断言读的那个东西，必须**就是**要证的那个东西。
   反例：日志出现 READY ≠ 端口可连（m150）· 用 UDP 探针证明「网通」却去测 TCP 回退（m116 D5）。
   做法：就绪/前提类断言各自**单独自证一次**（正控 + 负控都写）。

盘点工具（离线，不是门）：`selfhost/audit_gate_flakiness.py`（静态名单）+
`selfhost/flake_rerun.sh`（动态频次）。detail 见 `docs/GATE_FLAKINESS_AUDIT.md`。

### 二·补 M343：第 7 例是「**判据读了两个不是一回事的数字**」

599（m317 [5.3]）的病根既不属于「时间量」也不属于「取样次数」，而是**第 6 条的变体**：
两个计数看起来是一对（`time_runs` / `idle_runs`），实际**生产者不对等**（2 个 ⇄ 1 个），
于是「严格相等」这条断言把「计数语义」当成了「产品行为」。
⇒ 补第 7 条口径：

7. **断言两个数相等前，先证明它们的生产者是同一处**。若一方有多个自增点（不同路径），
   相等只在「另一些路径从没跑过」时才成立 —— 那是**前提**，必须单独断言（或改成差额界）。

同时第 3 条（同一事实只读一次）在本例里被我误解成「两次采样要一致」——
**错**：计数本身就是单调递增的，「两次相等」永不成立（首版当场自伤判红）。
正确做法 = **同一次读数内取齐**（同一条 dump 行）+ 多次采样**单调不减**（递减即撕裂）。

### 二·补 M344：第 8 例（缺陷 600）是「**窗口比被测现象的抖动还短**」，而且单位写错了

m120 C 轨「偶发 rc=0」压了两轮（588 只记了频次、没定性）。本轮定性：

```
判据写的窗口：sleep(1.5)，注释「1.5 秒」  ← 单位错，sleep 单位是毫秒（同门用例 7 自己就写着 M304 实测）
真实窗口：1.5ms     线程启动抖动实测：6~32ms（进程总寿命上限）
⇒ 窗口比抖动小一个数量级：主线程到点退出，协程还没跑进去 ⇒ 没错误可报 ⇒ rc=0 是**合法**的
实测：1.5ms 16/300 rc=0（5.3%）· 200ms 0/300
负控回放：把窗口改回 1.5ms、K=30 ⇒ 3/30 rc=0，且「协程已启动」前提断言缺的正好是同一批迭代（3/12/27）
```

⇒ 补第 8 条口径：

8. **窗口类判据先验两件事：单位，和抖动上限**。注释里写「N 秒」必须写成实测过的单位
   （本仓 `sleep` 是**毫秒**）；窗口必须 ≥ 被测抖动实测上限的若干倍。
   并且**每轮都要断言前提真的发生了**（本轮的「协程已启动」）—— 否则窗口没够时，
   判据读到的是「现象没发生」，会被当成「产品没问题」。**假绿比假红危险**。

### 二·补 M344 之二：汇总/上报通道也要守第 6 条（缺陷 601）

频次实验第一版汇总报「12 门 × 5 轮 0 命中」，而原始日志里明明有一条红 —— 汇总脚本从
`round*.log` 抓门名，可 shard_run 的每轮摘要**只给计数不给门名**。**判据要断言的那个事实，
必须从承载它的那条通道读**，这条对工具/上报脚本同样成立（工具假绿没人会去复核）。

### 二·补 M345：第 9 例（缺陷 602）是「**观测窗口的起点不是被测事件**」，外加两条判据顺序错

```
修前 run_case：起服务 → 注册循环**立刻**开始（240×50ms ≈ 12s）→ 就绪探测 → 起 8 个客户端 → 等 DONE
⇒ 窗口的起点在**服务启动**，压测的起点在**探测成功之后**；两者之间隔着一次不确定的探测
绿轮（空闲）：探测亚秒级完成，客户端与窗口重合 → 25~34s
红轮（分片并发）：探测被拖到秒级甚至耗尽 → 客户端整体落在窗口之后 → 200=0、失败=0、就绪=0
```

⇒ 补第 9 条口径：

9. **观测窗口的起点必须由被测事件的发起方触发**（负控/压测类门：窗口起点 = 压测侧"我已发压"），
   不能由「被测对象启动」隐式决定；并且**前提失败要与症状失败分开定名**
   （`premise-listen` / `premise-traffic` ≠ `red`）—— 否则「没看见」会被当成「没问题」（假绿），
   而「起不来」会被当成「红了」（假红）。
   定名之后**断言顺序**也要对：**症状先于流量下限**。本门实测：摘锁后握手会卡住，
   窗口内只落 49–56 个样本却有 11–16 个失败（22%~28%）—— 先判流量下限会把它误报成
   `premise-traffic`（把「红了」说成「没看见」，缺陷 601 同族）。

改造后频次（`/data/autodrive/m345_m245_stability.sh`，6 轮：空闲 ×3 + 8 核人造负载 ×3）：

```
6/6 绿；负控 A 6/6 判红（其中 2 次是 SIGSEGV rc=139，4 次是"握手卡住 + 失败 11~16 个"）
正判据每轮窗口内真实请求 708~878 次（修前绿轮 649~844，但红轮 0）
```

## 五 一条纪律（写给下一次的自己）

> 门红时，先回答两个问题再动手：
> ① 这条判据**观测的是什么通道**？它和**要证的事实**是同一条吗？
> ② 这个观测**看了几次**？现象本身有没有随机性？
> 两个问题都能答清楚，再决定是改产品、改判据，还是只登记。
> 答不清楚就只登记 —— 不许拿「改判据」掩盖真问题，也不许拿「重跑一遍」掩盖假红。
