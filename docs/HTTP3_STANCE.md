# HTTP/3 口径（当前：**实验性 · 不建议生产启用**）

> 本文件是「H3 现在到底能用到什么程度」的**唯一口径**。启动日志会打印
> `HTTP/3 listening udp/<port> …（实验性：未达生产就绪，见 docs/HTTP3_STANCE.md）`。

| 项 | 状态 |
|---|---|
| 构建档 | ✅ 就绪（x86_64 默认链入 ngtcp2/nghttp3；aarch64 合法缺席：`quic_*`/`h3_*` = 0，见 M201 `native_symbols()` 门） |

## 二 已知缺陷与处置（如实登记）

| 编号 | 现象 | 状态 |
|---|---|---|
| **505** | **并发连接互相干扰**（M293 登记 → **M294 已修**，根因 = 缺陷 **507**）：同一个托管 listener 上**同时存活**的多条 H3 连接之间会互相污染。实测症状：服务端把某个连接的请求解成**空路径**（→ 404）或**另一条连接的路径**，或该连接**完全收不到响应**。**串行 12/12 全对 ⇒ 并发是触发条件**（N=2 即可复现）。取证：服务端 access 日志出现 `GET  404`（路径为空）或**两条连接记成同一路径**（如 `GET /probe/t1` 出现两次）；客户端侧分别表现为 `TIMEOUT` / `bad-status 404` / 收到别人 body。⚠️ 与 327 **不同族**：327 是**槽位复用后**（连接已结束）继承旧会话，本条是**同时存活**的连接互相干扰；327 的「连接代次」身份判据对它无效 | ✅ **已修（M294）** —— 根因见下一行；回归门 `examples/m294_h3_qpack_share/`（重复服务路径数 == 0 为直接指纹） |
| **507** | **`bi_qs_open` 的会话占用不是原子的**（M294 定位并修复）：占用是**无锁的「读 — 清 — 置位」三步**，其中 `memset(s, 0, sizeof(*s))` 会把**刚占上的占用位又清回 0** ⇒ 并发连接的第二个线程在窗口里**二次认领同一个会话槽** ⇒ 多条**同时存活**的活跃连接**共享同一张 QPACK 动态表** ⇒ 各自解出**别人的路径**（= 505 的全部症状）。实证：conn 13/14/15/16/17/18 **六条同时拿到 qd=13**、随后六条都解出同一路径。**修法**：占用位独立成数组（`g_qds_used`）+ **原子交换作唯一仲裁者**；`qd_sess.used` 字段已移除（结构上消除复发） | ✅ **已修（M294）** —— `shared 58→0` · 同一路径被服务多次 **有→无** · 客户端串味 **1~3→0** |
| **508** | **QUIC 连接槽位耗尽**（M294 登记为现象 → **M295 全收口**）。**修前**：① 上限被**硬编码在三个文件里、各写死 64** —— `QUIC_CONN_MAX`（QUIC 连接槽）· `H3_MAX_CONN`（H3 会话表）· `QD_MAX_SESS`（QPACK 动态表会话）；② 满了以后 `quic_alloc_conn` 返回 −1 且**完全静默**（客户端只见 `connect-fail`，服务端日志**零线索**）；③ `quic_close` **不发 CONNECTION_CLOSE**（直接 `ngtcp2_conn_del`）⇒ 「优雅关闭」与「进程被杀」在服务端看来**一模一样**，只能等空闲超时才回收（实测 **~10s**，受 `PX_H3_IDLE_MS` 主导：IDLE=1000 ⇒ 3.1s）。**修后**：上限收敛为 `runtime.h` 的 **`PX_QUIC_CONN_MAX 256`**（三处引用它，单一真相）· `cidtab` 按比例 2048 · **满了记账 + 限流报告 + 新 native `quic_pool_stats()`** · `quic_close` 先写终止包（对端**立即**回收）· `pthread_create` 失败不再泄漏槽位 · `g_qds` 改按需分配（**BSS 76.5MB → 9.4MB**）。实测：**abrupt 串行 300：首次失败 64 → 256**；**grace 串行 300：正确 81 → 300（全绿）**；DRAINING 刷屏 300 行 → 0 | ✅ **已修（M295）** —— 回归门 `examples/m295_quic_slot/`（35 通过 / 0 失败 · 4 道负控）
| **504** | **连接迁移（`quic_migrate`）在托管 listener 下必失败**（M293 新登记 · **未修**）：迁移后同一连接再发请求**永远收不到响应**（客户端 7/7 `post timeout`）。服务端 `strace` 决定性取证：`remote_sa` 在**旧源/新源之间来回抖**（`sendto → 旧源` · `recvfrom ← 新源` · `sendto → 又回旧源`）⇒ 正是 `bi_quic_migrate` 注释里写的「**迟到的旧源包把服务器 remote_sa 回切到已关闭的旧地址**」；那里的「切换前泵 300ms」在托管 listener（单 fd + DCID 路由）下**不足**。⚠️ **不是「迁移本身不支持」**：`examples/m54_s3_migrate_verify.sh` 的**裸 QUIC**（demo accept 路径）迁移 **PASS** | ⬜ **未修**（登记在 `examples/m293_h3_robustness/MIGRATE_KNOWN.tsv`，门做**双向核对** ⇒ 哪天修好会判「登记过期」逼更新本文件） |
| **327** | **连接槽位复用 ⇒ h3 会话状态串味**：h3 会话状态（QPACK 动态表 / 流缓冲 / `last_sid`）按 **conn 号**（= QUIC 槽位号）索引，而槽位**可复用**；`h3_conn_setup_c` 的幂等短路只看 conn 号 ⇒ 新连接继承**上一个连接**的 QPACK 上下文 ⇒ QUIC 层一切正常（能收能 ACK）、H3/QPACK 层编码与对端不一致 ⇒ **客户端永远读不到响应**，且**不自愈**（直到进程重启） | ✅ **M225 已修**（连接回收钩子 + 幂等判据带「连接代次」身份；门 `examples/m225_h3_conn_reuse/`，3 道负控） |

> ⚠️ 触发条件比最初报告更宽：**不需要"客户端非优雅断开"** ——
> 「连接正常关闭（或空闲超时）→ 槽位释放 → 新连接复用同一 conn 号」即可复现。
> 实测：本机 `PX_H3_IDLE_MS` 设小后，**连续 6 次普通请求**中第 4 次起全部超时
> （服务端仍照常处理并记 access 日志 —— 这是最容易误判为"网络问题"的形态）。

## 三 待办（下一轮候选，逐条都有独立编号计划）

1. ~~**0-RTT / 连接迁移路径下的 h3 会话复用**：与 327 同族，尚未覆门~~ ⇒ **M293 已覆门**：
   0-RTT 会话恢复 **✅ 正常**（`hd_before=false resumed_after=true`，回归门会话 E）；
   连接迁移 ⇒ **实测不可用**，登记为**缺陷 504**（见 §二）。
2. ~~**`ERR_DRAINING` 期间的读路径忙自旋尚未量化**~~ ⇒ **M293 已量化并关闭**：
   长空闲 20s 窗口 CPU 增量 ≤4 tick（<1% 核），全程 `ERR_DRAINING` 计数 **0**
   —— 晨曦现场那个「`ERR_DRAINING` 刷屏」现象在本机**不复现**。回归门把它作为**计数**断言（须为 0）。
3. **H3 无独立运行时指标**（连接数 / 丢包 / draining 计数）—— 上线前需要可观测性。
4. **`quic_listen`+`quic_accept` 的 demo 路径**不经连接回收钩子（其 conn 状态随 `memset` 复位）——
   若将来把它也接进托管路径，需同步覆门。
5. ✅ **并发连接互相干扰（缺陷 505）—— 已于 M294 定位并修复**（根因 = 缺陷 **507**，见 §二）。
   下面是当时的复现手法（保留，因为它是**回归门的语料来源**）；注意 **508 会掩盖 507**，连接数必须压在预算内。
   复现（本机，~10s）：
   ```
   # 起一个托管 listener，然后并发发起 N 条各带不同路径的 H3 请求
   for i in $(seq 12); do M293_HTTP_PORT=<port> M293_TAG=t$i ./build/cli_tag & done; wait
   # 观测：多数 OK，但约 1 例 TIMEOUT / bad-status 404；服务端 access 日志出现空路径或**重复路径**
   ```
   实测（9 轮）：8 轮 ≥1 例异常（多数恰好 1 例），1 轮 12/12 全对 ⇒ **概率性**。
   ⇒ 回归门 `examples/m293_h3_robustness/` 的 [8b] 层**只测量 + 登记**，
   **不硬断言「异常必须存在」**（概率性硬断言会偶发判红 —— 而「会偶发判红的门等于没有门」，M274 缺陷 480）；
   硬判据只设**下限**（≥8/12 正确）与「服务仍存活」，用于捕捉「listener 被拖垮」这类崩塌。
   **根因（M294 定位）**：候选 ①（服务端 per-connection QPACK 会话被共享）**成立**，但**不是「会话被共享」这么简单** ——
   是**会话分配本身不是原子的**（`memset` 把占用位清回 0 ⇒ 二次认领）。候选 ②（DCID 路由投错连接）**已否证**
   （`cid_full` / `stale` / `race` / `rsa_change` / `epoch_mismatch` / `exhaust` 六项计数器全 0）。
   ⚠️ **三代检测器全部失效**（v1 空操作 / v2 无守卫假阳 / v3 充要条件写错）—— 教训：
   **判据必须贴着「认领这个动作的完整边界」写**；若「认领」包含后续初始化，那么**初始化把标志位清零**就是认领的一部分。

3. **新建连接的速率受 router 单线程限制**（M295 新量出 · 未修）：256 个客户端**同时**建连时，实测只有 **63** 个成功 —— 而当时**槽位只占了 184/256**（即**不是**上限问题）。router 逐包串行处理，每条新连接要 `quic_srv_new_conn`（SSL_CTX/ngtcp2 初始化）⇒ 处理不过来时客户端握手超时。⇒ 这是**速率**问题（不是**上限**问题），与 508 **不同族**；需先量化「单条新建连接的服务端成本」再决定（分片 / 批量 / 预建）。

## 四 生产启用前置条件（建议按序满足）

1. ✅ **阻塞级缺陷 327 已修**（M225）—— 并有回归门；
2. ✅ **回归**：M293 门 `examples/m293_h3_robustness/` 已覆盖「非优雅断开 × N（串行 8 + **并发 12**）+ 正常连接穿插（交错 10 + 突发 4）+ 长时间空闲后重连（20s）+ 0-RTT 会话恢复」混合场景，含资源收敛（fd 恒定 / 无忙自旋 / RSS 有界）；
2b. 🟡 **缺陷 505（并发干扰，M294）与 508（槽位耗尽静默，M295）均已修** ——
    仍缺 **504（迁移不可用）** 与 **新建连接速率（§三 第 3 条：router 单线程）**；
3. ⬜ **放行 UDP**：`firewall-cmd --zone=public --add-port=443/udp`（**且 `--permanent`**，三节点都要）；
4. ⬜ **CDN / 边缘决策**：`Alt-Svc` 由**源站**发出，若源站在 CDN 后面而 CDN 不透传 UDP，
   客户端会拿 `h3=":443"` 去连**边缘** ⇒ 属自找麻烦。只在**直连客户端**的节点开，或统一在边缘开；
5. ⬜ **可观测 / 回退**：UDP 探活 + 一键关 H3（改配置重启）预案；
6. ⬜ **客户端侧**：本机 curl 7.76.1 **不带** `--http3`；PuXian 自研 H3 客户端（`examples/m225_h3_conn_reuse/`）
   可用于冒烟，但不作为生产验证的唯一通道。
