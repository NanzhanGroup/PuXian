## 二 已知缺陷与处置（如实登记）

| 编号 | 现象 | 状态 |
|---|---|---|
| **505** | **并发连接互相干扰**（M293 新登记 · **未修**）：同一个托管 listener 上**同时存活**的多条 H3 连接之间会互相污染。实测症状：服务端把某个连接的请求解成**空路径**（→ 404）或**另一条连接的路径**，或该连接**完全收不到响应**。**串行 12/12 全对 ⇒ 并发是触发条件**（N=2 即可复现）。取证：服务端 access 日志出现 `GET  404`（路径为空）或**两条连接记成同一路径**（如 `GET /probe/t1` 出现两次）；客户端侧分别表现为 `TIMEOUT` / `bad-status 404` / 收到别人 body。⚠️ 与 327 **不同族**：327 是**槽位复用后**（连接已结束）继承旧会话，本条是**同时存活**的连接互相干扰；327 的「连接代次」身份判据对它无效 | ⬜ **未修**（本轮只登记 + 测量；根因待插桩定位） |
| **504** | **连接迁移（`quic_migrate`）在托管 listener 下必失败**（M293 新登记 · **未修**）：迁移后同一连接再发请求**永远收不到响应**（客户端 7/7 `post timeout`）。服务端 `strace` 决定性取证：`remote_sa` 在**旧源/新源之间来回抖**（`sendto → 旧源` · `recvfrom ← 新源` · `sendto → 又回旧源`）⇒ 正是 `bi_quic_migrate` 注释里写的「**迟到的旧源包把服务器 remote_sa 回切到已关闭的旧地址**」；那里的「切换前泵 300ms」在托管 listener（单 fd + DCID 路由）下**不足**。⚠️ **不是「迁移本身不支持」**：`examples/m54_s3_migrate_verify.sh` 的**裸 QUIC**（demo accept 路径）迁移 **PASS** | ⬜ **未修**（登记在 `examples/m293_h3_robustness/MIGRATE_KNOWN.tsv`，门做**双向核对** ⇒ 哪天修好会判「登记过期」逼更新本文件） |
| **327** | **连接槽位复用 ⇒ h3 会话状态串味**：h3 会话状态（QPACK 动态表 / 流缓冲 / `last_sid`）按 **conn 号**（= QUIC 槽位号）索引，而槽位**可复用**；`h3_conn_setup_c` 的幂等短路只看 conn 号 ⇒ 新连接继承**上一个连接**的 QPACK 上下文 ⇒ QUIC 层一切正常（能收能 ACK）、H3/QPACK 层编码与对端不一致 ⇒ **客户端永远读不到响应**，且**不自愈**（直到进程重启） | ✅ **M225 已修**（连接回收钩子 + 幂等判据带「连接代次」身份；门 `examples/m225_h3_conn_reuse/`，3 道负控） |

> ⚠️ 触发条件比最初报告更宽：**不需要"客户端非优雅断开"** ——
> 「连接正常关闭（或空闲超时）→ 槽位释放 → 新连接复用同一 conn 号」即可复现。
> 实测：本机 `PX_H3_IDLE_MS` 设小后，**连续 6 次普通请求**中第 4 次起全部超时
> （服务端仍照常处理并记 access 日志 —— 这是最容易误判为"网络问题"的形态）。

## 三 待办（下一轮候选，逐条都有独立编号计划）

1. ~~**0-RTT / 连接迁移路径下的 h3 会话复用**：与 327 同族，尚未覆门~~ ⇒ **M293 已覆门**：
   0-RTT 会话恢复 **✅ 正常**（`hd_before=false resumed_after=true`，回归门会话 E）；
   连接迁移 ⇒ **实测不可用**，登记为**缺陷 504**（见 §二）。
2. ~~**`ERR_DRAINING` 期间的读路径忙自旋尚未量化**~~ ⇒ **M293 已量化并关闭**：
   长空闲 20s 窗口 CPU 增量 ≤4 tick（<1% 核），全程 `ERR_DRAINING` 计数 **0**
   —— 晨曦现场那个「`ERR_DRAINING` 刷屏」现象在本机**不复现**。回归门把它作为**计数**断言（须为 0）。
3. **H3 无独立运行时指标**（连接数 / 丢包 / draining 计数）—— 上线前需要可观测性。
4. **`quic_listen`+`quic_accept` 的 demo 路径**不经连接回收钩子（其 conn 状态随 `memset` 复位）——
   若将来把它也接进托管路径，需同步覆门。
5. ⭐ **并发连接互相干扰（缺陷 505）** —— **本轮最深的一条**，也是「H3 上线」当前的**头号拦路**。
   复现（本机，~10s）：
   ```
   # 起一个托管 listener，然后并发发起 N 条各带不同路径的 H3 请求
   for i in $(seq 12); do M293_HTTP_PORT=<port> M293_TAG=t$i ./build/cli_tag & done; wait
   # 观测：多数 OK，但约 1 例 TIMEOUT / bad-status 404；服务端 access 日志出现空路径或**重复路径**
   ```
   实测（9 轮）：8 轮 ≥1 例异常（多数恰好 1 例），1 轮 12/12 全对 ⇒ **概率性**。
   ⇒ 回归门 `examples/m293_h3_robustness/` 的 [8b] 层**只测量 + 登记**，
   **不硬断言「异常必须存在」**（概率性硬断言会偶发判红 —— 而「会偶发判红的门等于没有门」，M274 缺陷 480）；
   硬判据只设**下限**（≥8/12 正确）与「服务仍存活」，用于捕捉「listener 被拖垮」这类崩塌。
   根因**未定位**（两条候选：① 服务端 per-connection QPACK 会话被共享；② DCID 路由把包交给错连接）——
   需插桩构建才能区分。

## 四 生产启用前置条件（建议按序满足）

1. ✅ **阻塞级缺陷 327 已修**（M225）—— 并有回归门；
2. ✅ **回归**：M293 门 `examples/m293_h3_robustness/` 已覆盖「非优雅断开 × N（串行 8 + **并发 12**）+ 正常连接穿插（交错 10 + 突发 4）+ 长时间空闲后重连（20s）+ 0-RTT 会话恢复」混合场景，含资源收敛（fd 恒定 / 无忙自旋 / RSS 有界）；
2b. ⬜ **必须先修缺陷 505（并发干扰）与 504（迁移）** —— 否则「并发」这条腿在生产上仍不可用；
3. ⬜ **放行 UDP**：`firewall-cmd --zone=public --add-port=443/udp`（**且 `--permanent`**，三节点都要）；
4. ⬜ **CDN / 边缘决策**：`Alt-Svc` 由**源站**发出，若源站在 CDN 后面而 CDN 不透传 UDP，
   客户端会拿 `h3=":443"` 去连**边缘** ⇒ 属自找麻烦。只在**直连客户端**的节点开，或统一在边缘开；
5. ⬜ **可观测 / 回退**：UDP 探活 + 一键关 H3（改配置重启）预案；
6. ⬜ **客户端侧**：本机 curl 7.76.1 **不带** `--http3`；PuXian 自研 H3 客户端（`examples/m225_h3_conn_reuse/`）
   可用于冒烟，但不作为生产验证的唯一通道。
