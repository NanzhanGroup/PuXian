## 〇、一句话结论

**native 机器码在 PuXian 当前形态下的性能天花板 ≈ 现有 C 轨（1.04~1.5x VM），而这个天花板今天已由
`px build --c` 逃生舱免费提供；真·自研 AOT 后端的成本却是季度级（4 架构 × GC map × 安全点 × 协程兼容 × ABI）。
因此不建议现在启动「自研机器码 AOT 旗舰」——建议 M104 改为「性能增强」：① LTO 构建档（0 代码改动，
本次实测纯计算 1.16x）+ ② VM 内联缓存/超指令（1.2~1.5x），合计 2~4 周即可吃掉 VM↔C 轨大部分差距；
native 留到「去 C 工具链依赖成为硬需求」或「类型特化去箱化」时再启动。**

若目标不是性能而是「自举到自己的机器码」这一**语言成熟度/战略**目标，则应重新定义为单独立项（见 §八·路线 C），
且必须接受其**性能回报有限**（见 §二）与**工期 4.5~6 个月**（见 §七）。

## 一、native 的三条候选形态（先厘清"native"到底指什么）

"native 后端"在 PuXian 现状下不是一个选项，而是三个成本差一个数量级的选项：

| 形态 | 含义 | 现状 | 成本量级 |
|---|---|---|---|
| **A. C 后端（已有）** | AST → C 文本 → gcc -O2 → 机器码 | ✅ **已存在**：`px build --c`（M91 起为逃生舱）；M89 前为默认轨 | 0（已交付） |
| **B. BC → C 瘦后端** | 字节码 BCModule → 生成 C 函数 → gcc 编译 | ❌ 不存在（现有 VM 轨是「BC 数组 + 解释器」，不是「BC → 代码」） | 2~4 周（若可行） |
| **C. 自研机器码 AOT** | 字节码 → 指令选择 → 寄存器分配 → 机器码/汇编 | ❌ 不存在；全仓无 JIT/AOT/代码生成器（grep 确认；仅 `runtime/arch_*.h` 有读 SP 的内联汇编，属 M67 GC 架构层，与代码生成无关） | 18~25 周（P50，见 §七） |

> 关键事实：PuXian **今天已经能产出机器码**（形态 A）。所以"M104 native 旗舰"的真实含义只能回到
> **形态 C（自研后端，去 gcc 依赖）**，或退化为 B。以下分析以此为前提。

## 二、核心实测：native 的性能天花板 = C 轨 ≈ 1.04~1.5x VM

这是本报告最重要的结论，直接决定 native 的 ROI。

### 2.1 数据

| 来源 | 负载 | C 轨 / VM 轨 | 说明 |
|---|---|---|---|
| docs/M89_PERF_BASELINE.md | fib(28) 纯计算 | **1.52x** | 递归热点最坏情形 |
| docs/M89_PERF_BASELINE.md | compiler 综合负载 | **1.04x** | parse/codegen/bc_emit 全链 |
| docs/M89_PERF_BASELINE.md | http_json 服务 | **~1.00x** | 8 并发×200 |
| **本报告独立复测（2026-09-11）** | fib(30) 纯计算 ×3 | VM 5247/5275/5288ms vs C 4879/4817/4430ms = **1.12x** | 同源码、`--full` 双轨 |

### 2.2 为什么天花板只有这么低（代码级证据）

```
LXValue = { LXType type; union { bool; int64_t; double; LXObject*; } }   // 16B，带类型标签
LXValue px_add(LXValue a, LXValue b) {
    if (a.type == PX_STR && b.type == PX_STR) { ...分配+memcpy... }
    if (a.type == PX_INT && b.type == PX_INT) return px_int(a.as.i + b.as.i);
    if (a.type == PX_FLOAT || b.type == PX_FLOAT) ...
    if (a.type == PX_LIST && b.type == PX_LIST) { ...分配+逐项拷贝... }
    px_error("无法相加: %s + %s", ...);
}
```

- **每一个值操作都走 runtime 动态分派函数**（px_add/px_sub/px_lt/px_index/px_field_get/…）；
- **每一个 px 帧槽是 16B 带标签值**，无去箱化、无类型特化；
- 所以「C 轨」的真实形态不是"裸机器码"，而是**「机器码 + 动态值层」**——函数调用/跳转的开销只占
  小部分，**动态值层（类型判定 + 边界检查 + 分配 + 哈希查表）才是主成本**；
- VM dispatch 只是叠加在其上的一小层（每指令一次 switch + 取指），故 VM/C = 1.04~1.5x。

**推论**：手写 AOT 后端若沿用同一套 boxed 语义 + 同一套 runtime helper（必然如此，否则语义要重写），
其产出机器码的**每指令工作量与 C 轨同构**，唯一省下的是 VM dispatch 那一层 →
**性能收益上限被死锁在 1.04~1.5x**；而 gcc -O2 的寄存器分配/指令选择几乎必然优于手写后端 →
**手写后端大概率慢于 C 轨**（即收益可能为负）。

### 2.3 补充实测（本次新增）：C 轨 + LTO 免费加速 1.16x，VM 轨无效

既然瓶颈是"动态值层函数调用"，那**跨 TU 内联**（LTO）就应该有效。实测（fib(30) 中位，同源码）：

| 构建 | 轮次(ms) | 中位 | 相对 VM 默认 |
|---|---|---|---|
| VM 轨（默认，`-O2`） | 5247 / 5275 / 5288 | **5275** | 1.00x |
| VM 轨 + LTO（`--cc "gcc -flto"`） | 5745 / 5297 / 5118 | **5297** | 1.00x（噪声内，无效） |
| C 轨（`-O2`） | 4879 / 4817 / 4430 | **4817** | 1.10x |
| **C 轨 + LTO** | 4760 / 4145 / 4162 | **4162** | **1.27x** |

- **C 轨 + LTO 比 C 轨快 ~1.16x**（gcc 跨 TU 内联 px_add/px_call 等 runtime helper，正是 §2.2 的瓶颈）；
  链接耗时增加（~100s 首次，含 runtime LTO 重建），产物反而略小（9,104,800 vs 9,179,032 B）。
- **VM 轨 + LTO 无效**：VM 轨产物 C 只是 BC 数据表，热点在 918 行解释循环的 switch + helper 调用，
  LTO 无法有效内联 dispatch 路径（代码体量/间接性）。
- **含义**：这是**零代码改动的性能杠杆**（对纯计算/综合负载有效，IO 型无感），可直接作为
  `px build` 的可选构建档（如 `PX_BUILD_LTO=1`）纳入路线 B；同时也再次印证 §2.2——加速来自
  「减少动态值层的调用开销」，而非「把指令换成机器码」。

### 2.4 要真正加速，杠杆不在"机器码"，在"去箱化"

| 手段 | 预期收益 | 成本 | 备注 |
|---|---|---|---|
| VM dispatch 优化（超指令/内联缓存/常量缓存） | **1.2~1.5x**（吃掉大部分 VM↔C 差距） | 2~4 周 | **建议的 M104 方向** |
| 全局槽无锁化（GETG 直索引） | 服务型负载 1.0~1.2x | 已部分完成（M92/M89 GETG 槽） | 小 |
| 内联缓存（方法/字段/全局名解析） | 综合负载 1.1~1.3x | 1~2 周 | 纯 VM 内改动 |
| **类型反馈 JIT + 去箱化（LuaJIT 式）** | **3~10x**（真机器码的正确用法） | 6 个月+，高风险 | 研究级；与"native 后端"是两个项目 |
| 自研 AOT（boxed 语义不变） | **≤1.5x（可能为负）** | **4.5~6 个月** | 不划算 |

> 换言之：**"跑得快"的正解是"少做动态分派"（去箱化/JIT），不是"把同样的分派编译成机器码"。**

## 三、改造面量化（形态 C：自研 AOT 后端）

### 3.1 必须覆盖的指令面（已有明确边界，是利好）

- **57 个字节码 op**（runtime/vm.h，其中 vm.c 已实现 54），指令面已冻结、已是平坦三地址寄存器式
  → **IR 成熟度是最大利好**：不需要从 AST 重新设计中间表示，字节码就是 IR。
- 但要成为合格后端 IR，**缺三类信息**：
  1. **类型信息**：BCModule 全程 untyped（全是 LXValue 槽）→ 无法做算术去箱化/直接寄存器分配；
  2. **槽活跃性（liveness）/GC map**：VM 现为「帧存活期槽值保守全标」（vm.c 注释明示）→
     native 需 per-PC 的 GC 安全点 + 活跃槽位图，否则精确 GC 会误收/漏收；
  3. **调用/异常边界**：Result-Err 传播（TRY/RET）、px_error 致命（longjmp）、帧协程让出点
     （阻塞 native 调用）在机器码里都需显式建模为**安全点**。

### 3.2 架构乘法（成本 ×4）

CI 目标架构 = **x86_64 / aarch64 / armv7 / riscv64**（.github/workflows/ci.yml multiarch 矩阵）。
一个自研后端要 ×4 套：指令选择、寄存器分配、ABI/调用约定、栈帧布局、GC map 编码。
（对照：现有 C 轨靠 gcc 免费获得 4 架构 + qemu 验证。）

### 3.3 与运行时的接口面

- runtime 有 **306 个 native** + ~255 个 `px_set_global` 注册名 + 全量 boxed 值操作函数
  （px_add/px_index/px_field_get/px_call/px_gc_* 等，runtime.c 16,865 行）→ native 代码必须**逐一对齐**
  这些 helper 的调用约定与 GC 根语义；**没有"小而美"的 native 子集**可言。
- 精确 GC（M92）已就位 → 这是 native 的**大利好**（不再需要保守扫 C 栈），但前提是 native 自己能
  提供 **GC map + 安全点**，否则精确根面在 native 栈上失效（见 §四）。

## 四、GC 对接：M92 的成果如何变现，以及 native 的欠账

### 4.1 现状（M92 精确 GC，利好）

- 根面 = 全局槽 + **VM 帧槽数组**（`px_vm_gc_mark_state`：遍历 frames[0..nframes) 的 slots）
  + 线程 TLS 登记根栈（native 桥 `px_push_root/px_pop`，~60 处）；
- 整栈保守扫描（arch_scan_stack / registers / thread_stack）已在 precise 模式**退役**。

### 4.2 native 的欠账

| 问题 | 现状 | native 需做的事 |
|---|---|---|
| 帧槽位置 | 堆数组（帧栈在堆上，跨线程可遍历） | 若改 C 栈 → GC 看不见 → 必须提供 **stack map** |
| 槽活跃性 | 无（整帧全标，宁漏不误） | per-PC liveness → GC map（或沿用"整帧全标"，则需保持堆帧） |
| 安全点 | VM 每指令边界天然是安全点 | native 需在循环回边/调用点插入 safepoint check |
| 协程让出 | 堆帧 + 指针切换，零汇编（coro.c 注释实证） | 见 §五（这是最难的一条） |

> **结论**：GC 侧的最佳路径是**保留现有堆帧模型**（native 代码也操作堆上的帧槽数组，而非 C 栈）——
> 这样 GC/协程全部零改动。但这恰好意味着 native 代码与 VM 的"数据搬运"方式相同，**唯一省下的仍是
> dispatch 那一层** → 与 §二 结论闭环。

## 五、最关键约束：native 与「帧协程 M:N」的兼容性（成本黑洞）

M93–M102 建立的**帧协程模型是 PuXian 的资产，也是 native 的最大约束**：

```
coro.c 头注释（实证）：帧栈全堆上，切换只换指针（px_vm_bind/unbind），零 ucontext/零汇编。
```

- VM 的协程 = **堆上帧数组 + 指针切换** → 任意阻塞点（chan/mutex/sleep/网络/.px 子进程）可挂起/恢复；
- **原生 C 栈帧天然不可挂起**（无法在函数中途冻结 C 栈给调度器换出）。
- 因此 native 后端只有两条路：

| 路线 | 做法 | 后果 |
|---|---|---|
| **甲：保留堆帧** | native 代码把局部变量放堆帧槽（同 VM），调用/返回手写帧链 | 协程/GC 零改动；但**失去 C 栈/寄存器的局部变量优势** → 收益 ≈ dispatch 替掉 = ≤1.5x |
| **乙：栈式原生协程** | 栈拷贝或分段栈（Go 式）+ 精确 stack map + 栈增长/收缩 | 收益理论高，但 = **重造 Go runtime 的栈管理 + GC 栈图**，单这一项就是数月 |

**这条约束把 native 的成本从"写个代码生成器"抬到"写个运行时"**——是 §七 工期区间的最大来源。

## 六、ABI / 与 VM 互调

- 现有互调面：`px_call`（C 函数指针）+ `px_vm_entry`（统一函数对象 trampoline，vm.h D2 已就绪）
  → 若 native 函数也统一成 `LXValue(*)(LXValue*,int,void*)`，则 **vm↔native 互调零改动**（利好）；
- 但 native 函数若需挂起（协程），则 `LXValue` 签名无法表达"让出" → 需要 second stack / 状态机
  改写（把可挂起函数切成状态机，或走 §五·乙）。这是设计上的**主要开放问题**。

## 七、工期钉到周级（形态 C，全量可交付）

假设：单人全时、S 微步纪律、沿用双轨对拍（vm_ab 38 例 + diffcheck + 自举证明）为语义基准。

| 阶段 | 内容 | 周 |
|---|---|---|
| S1 设计 | IR 扩展（类型标注/liveness）+ 后端选型 + ABI + GC map/safepoint 方案 + 对拍 harness | 2~3 |
| S2 单架构最小后端 | x86-64：整数/控制流/调用（boxed，复用 runtime helper，不改帧模型） | 4~6 |
| S3 全指令面 + GC/协程 | 57 op 全覆盖 + 精确 GC map + 安全点 + 协程让出 + Result/Err 传播 + native 桥根 | 6~8 |
| S4 多架构 | aarch64 / armv7 / riscv64 三套后端 | 4~6 |
| S5 收口 | 双轨对拍 + 自举证明 + 全量回归 + 重链 + 文档 + 发布 | 2 |
| **合计** | | **P50 ≈ 18~25 周（约 4.5~6 个月）；P90 ≈ 30+ 周** |

- **最小可行 toy**（单架构、无协程、仅整数/控制流）= 6~8 周 —— 但**不可交付**（不覆盖语言语义、
  破坏协程），只能作技术验证。
- 对照：**VM 性能增强**（内联缓存 + 超指令 + 常量缓存）= **2~4 周**，收益 1.2~1.5x（吃掉大部分差距）。

## 八、三条路线对比与建议

| 路线 | 内容 | 收益 | 成本 | 风险 | 建议 |
|---|---|---|---|---|---|
| **A. 维持现状** | C 轨逃生舱（`px build --c`） | 热门程序即时 1.0~1.5x | 0 | 无 | 保留 |
| **B. 性能增强** | ①LTO 构建档（`--cc "gcc -flto"`，0 代码改动）+ ②VM 内联缓存/超指令/常量缓存 | **① 1.16x（纯计算，已实测）+ ② 1.2~1.5x，惠及所有程序** | **2~4 周** | 低（VM 内改动 + 构建开关，双轨对拍守护） | ⭐ **推荐作为 M104** |
| **C. 自研 AOT 旗舰** | 形态 C 全量 | ≤1.5x（可能为负）或需再叠 JIT 才有意义 | 18~25 周 | 高（协程/GC/4 架构） | 不推荐现在启动；若为战略目标另立"去工具链依赖"里程碑 |

### 什么条件下路线 C 才划算（启动门槛，供将来复核）

1. **去 C 工具链依赖成为硬需求**（自足工具链、无 musl.cc 交叉链、无需 gcc）——这是**产品/部署**理由，
   不是性能理由；且需再叠加"ELF 产出/链接/静态 libc"子项，成本再 +4~8 周；
2. **叠加类型特化（去箱化/JIT）**——但那时项目性质已是"JIT 旗舰"而非"AOT native 后端"；
3. **战略：自举到自己的机器码**（语言成熟度里程碑，M88 §四·A「元循环自举是另一回事，更得排最后」）。

### 与 M88 裁定的关系（复核）

M88 §四·A 裁定 "③ native 排在 VM 化 + C 类之后"，其**排序理由完全成立**（VM/IR/GC 前置已由
M89–M92 兑现）。但裁定当时**未量化 native 的实际收益上限**；本报告补上这一数据后，"排在最后"
应升级为"**在当前语义（全 boxed）下收益有限，非必要不启动**"——排序与门槛是两件事。

## 九、风险清单（若将来启动路线 C）

| 风险 | 证据/影响 | 预案 |
|---|---|---|
| 收益为负（手写后端不如 gcc -O2） | §2.2 分析 | 启动前先做 S2 单函数对比（native vs C 轨同函数），不达标即止损 |
| 协程不兼容（C 栈不可挂起） | §五 coro.c 实证 | S1 定稿前先决策甲/乙路线；乙路线需独立评估栈管理 |
| GC map 缺失 → 精确 GC 失效 | §四 | 保留堆帧（甲路线）或在 S1 设计 stack map 编码 |
| 4 架构乘法 | CI multiarch 矩阵 | 先 x86-64 单架构验证，再平移；可考虑只做 1~2 个一等架构 |
| 与 VM 双轨语义漂移 | vm_ab 38 例 + diffcheck + 自举证明 | 新后端必须同过两组对拍（第三种实现原则，M89 已立） |
| 构建期依赖（as/ld） | 现有 pxc 依赖 cc | 若目标"零工具链"，需自产 ELF → 单列子项 |

## 十、S1 结论与建议动作

1. **可行性判定**：形态 C（自研 AOT）技术上可行（IR 成熟、精确 GC 已就位、ABI 兼容面清晰），
   但**性能 ROI 极低**（≤1.5x，且与已有 C 轨重叠），**成本高**（18~25 周 P50）；
2. **建议**：**M104 改为「性能增强」**（路线 B：① LTO 构建档（0 代码改动，实测 1.16x）+ ② VM 内联缓存/超指令（1.2~1.5x），合计 2~4 周 / 低风险），
   把 native 记录为"有明确启动门槛的候选旗舰"（见 §八·门槛）；
3. **待拍板**：
   - 选项 ①：M104 = VM 性能增强（推荐）；
