## 2 ⭐ 两个被实测**否证**的假设（这是 B 项最重要的产出）

### 2.1 「4 路分片互相重复建 devbuild 产物」——不成立

| 指标 | 实测 |
|---|---|
| R2 全片 devbuild 调用 | 184 次（重建 138 / 复用 46） |
| 唯一 (件, key) | **130** |
| **跨片重复重建** | **8 次 ≈ 120s ≈ 墙钟 2.4%** |

原因：**76% 的调用发生在门内负控（打桩）状态**，每个门的打桩内容不同 ⇒ key 天然唯一 ⇒
**必须重建**，跨片也共享不了。真正可共享的只有「基线源码」那批，而它们已经被各片自己的
多槽缓存（M287）命中（复用 46 次）。

⇒ **共享产物槽的收益 ≈ 2 分钟，且引入并发写同一 key 的风险** ⇒ 按 M104
「量化表否定的子项立即降级」：**不做**。

### 2.2 「把分片调度调平」——上限只有 6.5%

理想均分 3,280s ⇄ 实测最长 3,623s ⇒ 即使完美平衡也只省 **343s（约 5.7 min）**。
而各门耗时本身抖动 ±20–40%（M310 丙2 实测），**调度器无法预测到比这更准**
⇒ 再投入的边际收益极低。**不做**。

## 3 真正剩下的杠杆（按收益排序，附实验协议）

| # | 杠杆 | 潜在收益 | 风险 / 前置 |
|---|---|---|---|
| **L1** | **quiet 段瘦身**：10 个「低负载门」里，只有少数是**真的时序敏感**（`m267_perf` 性能、`m280_resource` 资源、`m244_gate_parallel` 自身测并行）。其余（`m302`/`m291`/`m183`/`m295`/`m296`/`m120`）若实测不敏感，可按原样放回分片 | 最大 **~700s（13%）** | **必须先证明「不敏感」**：同一门在「4 路满负载」与「quiet」两档各跑 ≥3 次，比较 rc/关键数值是否稳定 |
| **L2** | 分片数 4 → 6/8 | 分片段 ≈ −25% | 核数 8 已满（每片 `GATE_JOBS=2`）；加到 6 路必须把 `GATE_JOBS` 降到 1，需实测总吞吐 |
| **L3** | 削减最贵的门（如 `m246` 624s：364 例 × 3 轨） | 单门 −30~50% | 只能靠「聚合驱动 + 门内并行」；`m246` 已在用 `gate_par`，余地小 |

⚠️ **红线**：任何一项都**不许**用「少跑门 / 放松判据」换时间。

## 4 怎么用

```bash
# 一轮分片跑完后
packaging/chain/gate_cost_report.py /data/gatevm/shard-YYYYmmdd-HHMMSS --top 12
# 关键看：④ 的「跨片重复」占比、①的「不平衡损失」、②的 quiet 段占比
```

判读口径：

- **④ 占比 < 3%** ⇒ 不要再谈「共享产物」；
- **① 不平衡 < 10%** ⇒ 不要再谈「调平」；
- **② quiet 占比 > 20%** ⇒ 只有 L1 值得做，且**先做敏感性实验**（不是先改调度器）。

---

## 5 覆盖边界

1. 本模型基于**一次** R2 实测（216 门 · 本机 8 核 · `GATE_JOBS=2` + 绑核）。换机器/换分片数要重跑。
2. `④` 的 15s/次是 M287 实测的**平均**重建成本；冷 `.rtcache` 轮次会更贵（M306 实测该门 1201s）。
3. quiet 段的「低负载」定义来自宿主侧 `/data/gatevm/quiet_needed.txt`（带理由），本文件不复制它。
