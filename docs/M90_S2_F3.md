# M90-S2 · F3 快查报告 —— http_serve keep-alive 高并发崩溃（15s 空闲超时误杀活跃连接）

> 完成（2026-09-09，dongyue）：M89_PERF_BASELINE 附带发现 F3「HTTP 20 并发双轨
> RPS 骤降（~1300→~340）+ max ~9s 尖刺」的根因快查。**判定：真 bug（非压测伪影），
> runtime 服务层（M88-B-S2 事件化 keep-alive 遗留），与 VM/C 轨无关**。
> 证据链 + 已试修复记录 + 修复方向见下。修复落地列为独立批次（F3-fix）跟踪。

## 1. 复现与量化（同机，C 轨 http_json server，press_http.py keep-alive 压测）

| 压测 | RPS | ok/total | max | 现象 |
|---|---|---|---|---|
| 8 并发 ×2000/线程（M89 基线同参数） | 249~301 | ~50-65% | **16.6-17.7s** | reset + 连接悬挂 |
| 20 并发 ×2000/线程 | 233~285 | ~26-55% | **17.5s** | reset + 连接悬挂 |

- M89 基线记录 8 并发 1304 RPS 全 ok 的产物（http_json_c，同机）**现复测同样崩溃**
  → 非本次改动引入，非环境噪声（load 4.6 干净态复现）。
- **关键洞察：崩溃阈值 = 压测总时长跨越 ~15s**（keep-alive 空闲超时 PX_CONN_IDLE_TMO_MS）：
  M89 短测 8 并发 1304 RPS → 16000 req 12.3s 完成 **<15s 未触发**；本复现 RPS 慢
  （~300）→ 单线程 2000 req 需 ~50s >15s → 触发。任何 >15s 的 keep-alive 压测必崩。
- max 尖刺 16.6-17.7s ≈ 15s 空闲超时 + 客户端 socket timeout（20s）差值 → **活跃连接被
  「15s 空闲超时」误杀**（Connection reset by peer 佐证）。

## 2. 机制

M88-B-S2 事件化 keep-alive：
- worker 响应写完 → `px_fd_readable_now`（poll 0）探测无在途下请求 → 连接交 IDLE
  （`px_evc_idle_put`：epoll ET 注册 + state IDLE + 计时 idle_since）→ worker 释放。
- 事件循环（**单线程**）detect 该连接可读 → pop（IDLE→ACTIVE）→ 投回 fserve 池 →
  worker 处理下一请求突发。
- 空闲超时 tick：`now - idle_since >= 15000ms` → close。

**缺陷**：若某活跃连接交 IDLE 后，事件循环未及时/未能 detect 其下请求（ET 漏报、
派发路径竞态或单线程积压，**根因待 strace/epoll 事件日志深查**），连接在客户端持续
请求下被误判「空闲」，15s 后 tick close → 活跃连接 reset、客户端 socket 超时。
RPS 越高/连接越多 → 交 IDLE 越频繁 → 触发概率越高（20 并发比 8 并发易触发，与
M89 F3 观察一致）。旧 C 产物（无本次任何改动）同现 → 与轨无关，纯 runtime 服务层。

## 3. 已试修复与结果（均回退，防污染）

| 尝试 | 改动 | 结果 |
|---|---|---|
| 修复① 超时全表扫限频 1s（P2） | px_ev_loop 扫描 `now-last_scan>=1000` | 20 并发 RPS 247~285 **无改善** → 主因非全表 O(16384) 扫描 |
| 修复② worker 交 IDLE 前 3ms 短窗 poll 消化背靠背（P1） | http_conn_worker keep-alive 分支 | 20 并发 RPS 631 / max 24ms（尖刺消）但 8 并发退化 ~405 且 ok 率降 → 每请求 poll 延迟 + 偶发挂，**回退** |

结论：乒乓（worker↔事件循环）非主因；**核心 = 15s 空闲超时误杀活跃连接**。
（注：修复②测试期间机器曾被多轮残留 server/press 进程打到 load 90+，后续已清理
并在 load 4.6 干净态用**原版产物**复现崩溃，排除环境假象。）

## 4. 修复方向（F3-fix 独立批次）

1. **误杀兜底（低风险，先做）**：空闲超时 close **前 poll(0) 二次确认**——有在途
   可读数据 → 不 close，摘 IDLE → ACTIVE → 投回 fserve 池（恢复服务）；真空闲才
   close。杜绝活跃连接被 15s tick 误杀（reset/悬挂消除）。
2. **事件循环漏报根因深查（核心）**：strace -f -e epoll_ctl,epoll_wait,close 抓
   「交 IDLE 后客户端持续发请求但 >15s 无 epoll 事件」的连接，定位 ET 注册/唤醒/
   派发链路的丢事件点（可能点：ET + ADD 前已 pending 的语义、wake 管道丢失、单
   事件循环线程在 fserve_push 队满/慢派发时阻塞吞事件、detect 与 idle_put 竞态）。
3. 收尾回归：8 并发长压（>15s）全 ok、20 并发 RPS 恢复 ≥ 8 并发基线、issue28
   单连接 unix socket 场景不受影响、m89_perf bench_vm_vs_c.sh 三档全绿。
