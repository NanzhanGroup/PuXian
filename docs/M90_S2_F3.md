# M90-S2 · F3 快查报告 —— http_serve keep-alive 高并发崩溃（15s 空闲超时误杀活跃连接）

> ✅ **F3-fix 已落地（2026-09-09，dongyue）**：根因定位 + 双修复 + 全量回归通过，见文末
> 「6. F3-fix 结论」。核心结论：误杀活跃连接的**真根因不是 epoll 漏报**（S2 报告的
> 「事件循环漏报深查」方向被实证修正），而是 **M11 并发 GC（stop-the-world）与事件化
> fserve 池的交互**——256 个空闲 worker 在 cond_wait 中被 GC 信号暂停的协商开销 + 被暂停
> worker 卡 cond_wait 锁窗口 → 事件循环 fserve_push 长时间拿不到 g_fserve_mu → 连接
> 请求 15s 无人处理（表象即「活跃连接被 15s tick 误杀」）。修复：① 空闲 worker 注销
> GC 槽（fserve_gc_reg，治本）；② 超时 tick close 前 poll(0) 二次确认救回活跃连接（兜底）。

> 完成（2026-09-09，dongyue）：M89_PERF_BASELINE 附带发现 F3「HTTP 20 并发双轨
> RPS 骤降（~1300→~340）+ max ~9s 尖刺」的根因快查。**判定：真 bug（非压测伪影），
> runtime 服务层（M88-B-S2 事件化 keep-alive 遗留），与 VM/C 轨无关**。

## 1. 复现与量化（同机，C 轨 http_json server，press_http.py keep-alive 压测）

| 压测 | RPS | ok/total | max | 现象 |
|---|---|---|---|---|
| 8 并发 ×2000/线程（M89 基线同参数） | 249~301 | ~50-65% | **16.6-17.7s** | reset + 连接悬挂 |
| 20 并发 ×2000/线程 | 233~285 | ~26-55% | **17.5s** | reset + 连接悬挂 |

- M89 基线记录 8 并发 1304 RPS 全 ok 的产物（http_json_c，同机）**现复测同样崩溃**
  → 非本次改动引入，非环境噪声（load 4.6 干净态复现）。
- **关键洞察：崩溃阈值 = 压测总时长跨越 ~15s**（keep-alive 空闲超时 PX_CONN_IDLE_TMO_MS）：
  M89 短测 8 并发 1304 RPS → 16000 req 12.3s 完成 **<15s 未触发**；本复现 RPS 慢
  （~300）→ 单线程 2000 req 需 ~50s >15s → 触发。任何 >15s 的 keep-alive 压测必崩。
- max 尖刺 16.6-17.7s ≈ 15s 空闲超时 + 客户端 socket timeout（20s）差值 → **活跃连接被
  「15s 空闲超时」误杀**（Connection reset by peer 佐证）。

## 2. 机制

M88-B-S2 事件化 keep-alive：
- worker 响应写完 → `px_fd_readable_now`（poll 0）探测无在途下请求 → 连接交 IDLE
  （`px_evc_idle_put`：epoll ET 注册 + state IDLE + 计时 idle_since）→ worker 释放。
- 事件循环（**单线程**）detect 该连接可读 → pop（IDLE→ACTIVE）→ 投回 fserve 池 →
  worker 处理下一请求突发。
- 空闲超时 tick：`now - idle_since >= 15000ms` → close。

**缺陷**：若某活跃连接交 IDLE 后，事件循环未及时/未能 detect 其下请求（ET 漏报、
派发路径竞态或单线程积压，**根因待 strace/epoll 事件日志深查**），连接在客户端持续
请求下被误判「空闲」，15s 后 tick close → 活跃连接 reset、客户端 socket 超时。
RPS 越高/连接越多 → 交 IDLE 越频繁 → 触发概率越高（20 并发比 8 并发易触发，与
M89 F3 观察一致）。旧 C 产物（无本次任何改动）同现 → 与轨无关，纯 runtime 服务层。

## 3. 已试修复与结果（均回退，防污染）

| 尝试 | 改动 | 结果 |

## 4. 修复方向（F3-fix 独立批次）

1. **误杀兜底（低风险，先做）**：空闲超时 close **前 poll(0) 二次确认**——有在途
   可读数据 → 不 close，摘 IDLE → ACTIVE → 投回 fserve 池（恢复服务）；真空闲才
   close。杜绝活跃连接被 15s tick 误杀（reset/悬挂消除）。
2. **事件循环漏报根因深查（核心）**：strace -f -e epoll_ctl,epoll_wait,close 抓
   「交 IDLE 后客户端持续发请求但 >15s 无 epoll 事件」的连接，定位 ET 注册/唤醒/
   派发链路的丢事件点（可能点：ET + ADD 前已 pending 的语义、wake 管道丢失、单
   事件循环线程在 fserve_push 队满/慢派发时阻塞吞事件、detect 与 idle_put 竞态）。
3. 收尾回归：8 并发长压（>15s）全 ok、20 并发 RPS 恢复 ≥ 8 并发基线、issue28
   单连接 unix socket 场景不受影响、m89_perf bench_vm_vs_c.sh 三档全绿。

## 6. F3-fix 结论（2026-09-09 落地）

### 根因实证链（修正 S2 第 4 节「事件循环漏报深查」方向）

| # | 实验 | 结果 | 排除/指向 |
|---|---|---|---|
| 1 | ET→LT 对照 | 均漏报（tmo_save 10~20 次/110s） | 排除 ET 语义 |
| 2 | SAVE 插桩 idle_ev_cnt（IDLE 周期 epoll 上报次数） | 漏报连接 idle_ev_cnt=0，但高频 wait 日志显示**每批 epoll_wait 都含该 fd** | 非 epoll 不上报；是事件循环处理不到 |
| 3 | INCONSIST 抓拍（epoll 报事件但 state≠IDLE） | 0 次 | 排除 state/登记不一致 |
| 4 | MSG_PEEK + FIONREAD | 漏报连接缓冲有完整 74B `GET /api/check` | 确为活跃连接被卡 15s |
| 5 | **gdb 全线程栈抓拍（卡顿期）** | **事件循环卡 `fserve_push→pthread_mutex_lock(g_fserve_mu)`；254 空闲 fserve_worker 在 cond_wait 被 GC 信号暂停自旋（gc_stop_handler）；1 worker 执行 px_gc_collect→slab_reclaim_empty→munmap** | **根因 = GC STW 与空闲 worker 交互** |
| 6 | **PX_GC_THRESHOLD=999999999（禁自动 GC）** | **RPS 218→1400，tmo_save 归零，max 18s→17ms** | **实锤：GC 是唯一根因** |

机制：事件化 keep-alive 后 256 fserve_worker 绝大多数空闲 cond_wait；M11 GC 每次
STW 需暂停全部已注册线程（254 个空闲 worker 的信号处理/自旋/恢复协商）+ 被暂停 worker
卡 cond_wait 锁窗口 → 事件循环 fserve_push 长时间阻塞 → 无法 epoll_wait → 连接请求
15s 无人处理。

### 修复（runtime/runtime.c）

1. **治本**：`fserve_gc_reg()` —— fserve_worker 空闲（cond_wait 等 job）时**注销 GC 槽**，
   取到 job 处理前再注册。空闲 worker 栈上无 px 对象（job 仅 fd+kind int）→ 不参与 GC
   暂停安全；GC 只暂停在岗 worker（≤并发连接数）+ 主线程 → STW 协商成本大降，事件循环
   不再被锁阻塞。注册/注销持 g_gc_mu（与 GC executor 天然互斥）。
2. **兜底（第二道防线）**：事件循环空闲超时 tick close 前 `poll(0)` 二次确认——有在途
   数据（POLLIN）→ 活跃连接救回（重新登记 ACTIVE → 投回 fserve 池）；POLLHUP/ERR → 断开
   关闭；无事件 → 真空闲才 close。杜绝任何路径下活跃连接被 15s tick 误杀。
3. 诊断计数器（PX_EV_DIAG=1 门控，生产默认关零开销）：idle_put/detect/tmo_close/tmo_save
   每 5s 一行 + SAVE 明细（ev_reg/idle_ev_cnt/peek 内容）——未来再现可一键定位。
