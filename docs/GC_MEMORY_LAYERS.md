# GC 内存分层（M318）

> 「RSS 涨了」不是一个可行动的结论。**先问是哪一层在涨**，再决定改什么。

## 一 三层模型

| 层 | 含义 | 读数 | 谁负责 | 典型修法 |
|---|---|---|---|---|
| **① 活对象层** | 真在用的数据 | `live_objs` · `live_bytes` | 业务代码 | 少建缓存 / 及时释放引用 |
| **② 分配器层** | 已向 OS 要、未必在用的页 | `slab_bytes` · `slab_n` · `slab_free_slots` · `slab_fully_empty` | GC 判据 + 页归还 | 调触发间隔 / `SLAB_FREE_STREAK` |
| **③ 非 GC 内存** | 线程栈 / glibc arena / 运行时缓冲 | `RSS − slab_bytes − 活数据` | 运行时 / 部署参数 | 线程池大小 / `MALLOC_ARENA_MAX` |

**实测（本机 · 反代 2000 请求 · 编译轨）**：

| 档位 | anon | slab (`②`) | 对象数 | live (`①`) | runs |
|---|---|---|---|---|---|
| 开启（`PX_GC_MAX_INTERVAL_MS=1000`） | 24.5 MB | **3.0 MB** | 8147 | **62 KB** | 6 |
| 关闭（`=0`） | 37.8 MB | **12.7 MB** | 64794 | — （GC 未跑） | 0 |

⇒ 同一个 RSS 里，「活数据」与「分配器总量」相差 **两个量级**，剩下的 ~21 MB 是第③层
（实测 `threads=259`，每个线程栈 8 MB 虚拟 / ~20 KB 常驻）。

## 二 怎么读

### 程序内（推荐）

```px
var d = gc_diagnose()
# d["live_bytes"] / d["slab_bytes"] / d["runs"] / d["alloc_since_gc"] / …
```

14 个字段，全部是 int 或 bool ⇒ 可直接塞进 `json_stringify` 当 `/metrics` 的载荷。
Ma 这类长期在线的服务应当在健康检查里暴露它。

### 运维侧（日志）

```bash
PX_GC_STATS=1 PX_GC_STATS_INTERVAL=30 ./your-service
# ⇒ 每 30s 一行：[px-gc-stats] rss_obj_live=… live_bytes=…KB
#                [px-gc-stats] heap alloc_since_gc=…B trigger_bytes=…
#                [px-gc-stats] slab n=… map_bytes=…KB free_slots=… fully_empty=…
```

### 判据（先量，再改）

```
② / ①  < 3    ⇒ 分配器与活数据同量级 —— 分层没有意义，问题在别的层
② 停止增长    ⇒ 第②层已平台化（GC 判据有效）
② 线性增长    ⇒ 触发判据打不到（M317 的形状）
③ 线性增长    ⇒ 不是 GC 问题：查线程数、arena、运行时缓冲
```

## 三 为什么「第②层平台化」是最强的信号

第①层（活数据）涨有两种解释：**业务真的在缓存** 或 **对象泄漏**。
第②层涨只有一种解释：**GC 判据没打到**（因为 slab 只在 GC 的 `slab_reclaim_empty` 里归还）。

⇒ 报障时先看第②层的斜率，能一步把「泄漏」与「没回收」分开。

## 四 ⚠️ 否证记录：**自适应 GC 软上限（≈ GOGC 2×live）本轮实测不做**

**提案**：触发点从硬编码 `512 MiB` 改成 `max(2 × live_bytes, 下限)`（Go 的 GOGC=100 语义），
理由是 M317 给出的公式 `高水位 = min(512MiB, 速率 × 间隔)` 里那个 512 MiB 是死旋钮。

**实测结论：对本仓的负载形态无效。**

| 事实 | 数值 |
|---|---|
| 服务场景的活数据 | **62 KB**（2000~10000 请求实测稳定，不随负载涨） |
| 自上次 GC 的分配量峰值 | **1.9 MB**（`interval=1000` 档） |
| 当时的字节阈值 | **512 MiB** |
| ⇒ 字节判据是否曾触发 | **从未**（差 270 倍） |
| ⇒ 真正在触发回收的是 | **时间判据**（`time_runs` 随 interval 线性涨） |

⇒ 把字节阈值从 512 MiB 降到 8 MiB（或任何 2×live 的值）**不会有任何行为变化**，
因为 `alloc_since_gc` 从来就没到过那个量级。

**但这不等于自适应无意义**，它只是在「M317 已修」的前提下被**时间判据盖住了**。
若将来出现「活数据本身就是几十 MB、且分配速率极高」的负载（例如在进程内做批量 ETL），
届时应当**重新测量**再决策 —— 判据就是本文 §二 的三行。

> 纪律：**先证明要改的东西不是空操作**（M289 的同款教训：那次 `px_gc_ensure_main_thread()`
> 被证明是空操作，撤销不提交）。

## 五 判据（门 `examples/m318_mem_layers/`）

| 层 | 守什么 |
|---|---|
| [1] 静态 | `gc_obj_size` **纯读**（不调 `px_type_name` —— 会与容器守卫互递归）· 两处 sweep 都累加 · slab 读数**单一实现** · native 已注册 + 名册同步 · 容器创建即 `PX_KEEP` |
| [2] 三轨 | `gc_diagnose` 的**契约面**逐字节一致（14 字段 + 类型）—— 不比绝对值（解释轨自带 AST 堆） |
| [3] 分层 | 编译轨：`live ≤ 4MB` · `slab ≤ 16MB` · `slab / live ≥ 3` |
| [4] 负控 A | 关闭档 ⇒ `slab ≥ 2 × 开启档`（**相对判据**；绝对阈值会随机器漂移） |
| [5] 负控 B | 判据回放：用开启档读数冒充关闭档 ⇒ 必须判红；放大 3× ⇒ 必须判绿 |
| [6] 覆盖边界 | 见门内注释 |

## 六 已知边界

- `live_bytes` 是**上一轮 GC 结束**时的快照；GC 从未跑过时是 **0**（读作「未知」）。
- `gc_obj_size` 对 dict/struct **不计键内容** ⇒ 对大键集是**下界**（实测偏差 < 10%）。
- 第③层本工具只**间接**度量（`RSS − slab`），不逐项拆线程栈 / arena。
- 只对**编译轨**断言绝对值：解释轨自带 AST 堆（实测 `live` 646 KB vs 编译轨 103 KB）。
