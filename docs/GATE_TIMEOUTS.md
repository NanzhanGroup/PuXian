# 门超时口径（GATE_TIMEOUTS）

> **一句话**：**「这扇门该给多少时间」是门的一条属性，必须和门一起写在注册源里，并且被实测基线盯着。**
> 建立：M311（缺陷 532）· 实现：`selfhost/run_gates.sh`（机制）· `selfhost/gates.registry.sh`（声明）
> · `selfhost/check_gate_timeouts.sh`（守卫）· `selfhost/gate_time_baseline.sh`（基线生成）

## 2 机制：声明在注册源，三层优先级

```bash
# selfhost/gates.registry.sh（必须写在该门 `run` 行**之前** —— sourced 线性求值）
gate_timeout upstream_tests 1800
run upstream_tests bash selfhost/run_upstream_tests.sh
```

生效上限的解析顺序（`run_gates.sh` 的 `run()`）：

| 优先级 | 来源 | 用途 | 超时消息里显示为 |
|---|---|---|---|
| ① 最高 | 环境变量 `GATE_TIMEOUT_<门名>` | 临时排障 / A-B 实验 | `来源 env` |
| ② | **注册源 `gate_timeout` 声明** | **唯一事实源**（串行 / 分片 / D2 同源） | `来源 注册源` |
| ③ | `GATE_TIMEOUT_DEFAULT`（900） | 兜底 | `来源 默认` |

超时消息会**指名来源**，例：

```
⏱  upstream_tests（**超时**：902s ≥ 上限 900s · 来源 默认，rc=124）
```

⇒ 「红的时候读得出真因」是本仓纪律（M185 / M168），这条消息就是它的体现。

### 2.1 声明必须合法（写错即 rc=2，不许静默退回默认）

- 缺参 / 秒数非正整数 / **同名两条声明值不同** ⇒ `rc=2` 并指名。
- 理由：注册源是唯一事实源，写错了**静默退回 900** 就是又一个「以为声明了、其实没有」。

## 3 守卫：`check_gate_timeouts.sh`

| 判据 | 内容 | 为什么 |
|---|---|---|
| **P1 声明有效性** | 声明的门必须在门清单里（悬空 ⇒ 红） | 名字写错 = 声明静默无效 |
| **P2 贴上限** | 任一门「实测 ≥ 80% × 生效上限」⇒ **红**（含走默认档的门） | ⭐ **本条就是缺陷 532 的正面判据**：删掉声明后它立刻报 `upstream_tests 963s / 900s = 107%` |
| **P3 声明裕度** | 声明档必须 ≥ **1.5×** 基线实测 | 防「声明了也不够」（如 963s 的门声明 1000s） |
| **P5 规模锚点 + 提取器 1:1** | 门清单 ≥150 · 基线 ≥150 行；源码里 `gate_timeout` 行数 ⇄ 解析条数必须相等 | 防「提取器坏了 ⇒ 空集 ⊇ 空集」的**假绿**（M212 缺陷 288） |
| P4 残留 | 基线有、门清单没有 ⇒ ℹ️（只提示） | 改名/删门的残留，不该判红 |

**自证 9 条**（`--self-test`，且**默认档也会跑**）：S1 正常 · S2 悬空 · S3 贴上限（指名到 80% 数字）·
**S3b 判据自伤**（关掉 P2 ⇒ 同 fixture 不再红）· S4 裕度不足 · S5 声明无基线 ⇒ ℹ️ 不红 ·
S6 规模锚点 · S7 缺输入 ⇒ rc=3（不许当绿）· **S8 动态**（假注册源声明 2s ⇒ 真被 `run_gates.sh` 执行，rc=124）。

> S8 的意义：前 7 条只证明「判据逻辑对」，只有 S8 证明「**注册源的声明真的被执行器采用**」——
> 否则整套东西可能是一个漂亮的空壳。

## 4 运行期：配额告警（≥80%，**不判红**）

`run_gates.sh` 在某门用掉 **≥80% 生效上限**时打印：

```
⚠️ <门名> 配额告警：<elapsed>s / 上限 <cap>s（<pct>% · 来源 <src>）
     ⇒ 裕度不足 1.25×；口径与处理见 docs/GATE_TIMEOUTS.md（判红由 check_gate_timeouts 负责）
```

并在汇总里点名。口径说明：

- **不因此判红** —— 一个门偶尔慢不等于产品坏（M274 缺陷 480 的反面教训：判据贴边界会偶发假红）；
- 但必须在**当次**被看见 —— 否则就是缺陷 532 的重演：等它真红了，你会以为是产品回归。

## 5 基线：`selfhost/gate_time_baseline.tsv`（生成物，不许手改）

口径（M400 起）：

- 只收 `状态 != SKIP` 的行（SKIP 是「这轮没跑」，不是「耗时 0」）；
- **丢掉 `rc=124` 的行**（M400）：124 = 被上限**砍断**时的秒数，不是「这门需要多少」。
  把它当实测喂进来 ⇒ 基线直接等于上限 ⇒ 下一轮 P2 自己判绿，缺陷被自己的基线掩盖。
- 同一门出现在多份输入 ⇒ 取 **elapsed 最大**的那行（最坏情况）；
- 每行带 **来源列**（哪一份 TSV），可逐行追溯；
- **`--retain <旧基线>` 只补缺、不参与取最大**：否则「已修好的门」永远停在旧的最大值
  （M400 实测：m187 从 476s→261s，取全历史最大就永远显示 476s）。

### 5.1 刷新 = 自动的（M400 起，缺陷 763）

**不再手工跑。** M400 的病史是「输入回路没接上」：

| 事实（M400 实测） | 值 |
|---|---|
| 基线上次生成 | 2026-10-26 14:30（18 天前） |
| 基线行数 / 门清单 | 233 / 274 ⇒ **41 门 P2 从来判不到** |
| 生成器被谁调用 | **全仓无人调用**（只有本文写着「手工跑」） |
| 每轮 `shardN.times.tsv` | 都产出，**从未被消费** |
| 提交前门的计时表 | `mktemp` 后 `rm -f` —— 历史最高占用恰在那张被删的表里（m187 754s/900s = 83%） |

现在的回路：

```
全量门（8 分片 + quiet 车道）→ /data/gatevm/shard-<stamp>/*.times.tsv
提交前门（release_preflight.sh --gates）→ /data/gatevm/preflight-<stamp>.times.tsv（**不再 rm**）
        ↓  判绿后由 packaging/chain/release_postupgrade.sh 调
selfhost/refresh_gate_baseline.sh          # 窗口 = 最近 3 个「已完成」链（含 CHAIN-COMPLETE.txt）
        ↓  自动 commit + push（chore 提交，tree 脏则跳过不代你提交）
selfhost/gate_time_baseline.tsv            # 门清单有多少门，基线就有多少行
        ↓
check_gate_timeouts.sh  P2 裕度 · **P6 覆盖** · **P7 回灌新鲜度**
```

两条新判据（都在 `--self-test` 里有负控+正控）：

- **P6 覆盖**：门清单里每扇门都必须有基线行 —— 否则 P2 对它**根本判不到**（静默绿）。
- **P7 回灌新鲜度**：`/data/gatevm` 下存在比基线最新来源标签更晚的**已完成且判绿**链 ⇒ 红。
  「已完成」= 目录里有 `CHAIN-COMPLETE.txt`（链尾才写）；「判绿」= 目录里有 `GATE-VERDICT=GREEN`
  （`run_release_chain.sh` 判完后写）。正在跑的链两个都没有 ⇒ **天然不计**
  （否则判据会读自己，把正在跑的这一轮当成「未回灌」）。

  > **为什么红链不算「该回灌的实测」**（M400 首跑 r2 实测的锁死形态）：回灌只在**判绿后**
  > 由 `release_postupgrade.sh` 触发，红链不发布 ⇒ 永不回灌。若 P7 只认 `CHAIN-COMPLETE.txt`，
  > 一条红链就会让之后**每一轮**都红（实测：r1 链 20261113-183554 红 ⇒ r2 274 绿 1 红，
  > 唯一红的就是 P7）。判据必须与动作同口径：**只数「该回灌的」**。
  > 历史目录没有 `GATE-VERDICT` ⇒ 按「未判绿」跳过并 ℹ️ 报条数（不判红、不装作有数据）。
  > 红链的耗时数据仍会被回灌窗口（最近 3 轮）吃到 —— 那是数据，不是判据。

### 5.2 窗口语义（为什么是 3 轮）

取 max 会被「修复前的旧最大」永久钉住（M400 前 m187 476s 永不下降）。所以回灌只吃
**最近 N 个已完成链**（默认 3），下界随轮次滑动：某门修好后，等旧最大值滑出窗口，
基线就自动降下来 —— 不需要任何人「记得去改一个数」。

代价（如实登记）：修复的效果要**等 N 轮**才在基线里体现。这期间基线偏保守（偏高），
方向是安全的（不会漏报），只是数字旧。要立刻反映：`--stamps 1` 手跑一次。

### 5.3 新门首次入册（唯一需要人动手的场景）

新增门会让 P6 立刻变红（它还没有任何实测行）。补法 = 量一次再回灌：

```bash
GATE_TSV=/tmp/newgate.tsv ./selfhost/run_gates.sh --only <新门名> --allow-dirty
./selfhost/refresh_gate_baseline.sh --extra-tsv /tmp/newgate.tsv bootstrap-$(date +%Y%m%d) --commit
```

> 为什么不做「新门自动豁免」：豁免名单会腐烂，而「量一次」是 10 秒的事。
> 这条口径与 M212 缺陷 288 一致：**判据的输入必须可复算**，不许凭空补一个数。

## 7 覆盖边界（如实登记）

1. **基线是本机串行实测**。CI runner / 分片并行档的绝对耗时会不同（分片实测该门 898–902s，与串行同量级）；
   跨环境的裕度判断**不看绝对值，看形状**（M296s1 的教训：静态链接 ⇒ 分配器随产物走，绝对值不可跨发行版比）。
2. **配额告警不影响退出码** —— 它是「报警器」，不是「判据」；判据在 `check_gate_timeouts.sh`。
3. **P2 的 80% 阈值是口径选择**，不是自然常数；若要调整，**必须同时**调基线刷新流程与本文档（不要只改数）。
4. **未覆盖**：单个门的**内部分段**超时（例如 `run_upstream_tests.sh` 的 `--timeout 180` 是**单用例**上限，
   与本文件说的「门上限」是两层）。单用例上限若被顶穿会表现为该用例 TIMEOUT/FAIL，由门自己的判据负责。
5. 宿主侧 `/data/gatevm/shard_run.sh` 的按门硬编码已在 M311 删除（回归单一事实源）；
   它仍保留 `GATE_TIMEOUT_DEFAULT=900`，与仓库默认值一致。

## 8 超时与「核数 × 缓存冷热 × 仓库体积」的隐性耦合（M374 实测）

| 配置（同 HEAD `138b194`） | 结果 |
|---|---|
| 4 片 × `SHARD_JOBS=2`（每门 2 核）· `.rtcache` 冷 | **14 红**，其中 11 门顶格 900s；总 38642s |
| 4 片 × `SHARD_JOBS=4`（每门 4 核）· 同上 | **红 0**（251/251 绿）；总 170.5min |

- 受影响门型：**「负控后 `devbuild.sh` 重编 pxc / pxi」类** —— 门内两次全量自举编译，
  耗时 ≈ 常数 ÷ 核数；**2 核 + 冷缓存下稳定 >900s**（不是偶发）。
- 判据（写进 `packaging/chain/pick_gate_tier.sh` / `shard_run.sh` 口径）：
  1. **重烘轮次（bootstrap 指纹过期 ⇒ `.rtcache` 冷）强制 `SHARD_JOBS>=4`**；或
  2. 该类门做「上限 × 核数/2」线性放大（4 核时 900s 已够，无需调大常量）。
- **同一耦合在 CI 侧也成立（更严重）**：门内超时随「核数/缓存」变；**checkout 超时随「仓库体积」变**。
  M374 实测：仓库 10.0 GB；同体积下检出实耗 138s（定时）/ 20.4min（成功，差 40s 顶 20min）/
  20.0min 与 44.9min（未完成被 cancel）⇒ 体积 × 并发克隆数共同决定检出耗时，单看体积不足以解释。
  ⇒ 处置只能是**减少取数**（`filter: blob:none` 部分克隆 / 按需 `--depth=1`）或**瘦身仓库**，
  **不是调大 `timeout-minutes`**。
- **禁止的处置**：反复重跑等它偶然过 —— 那不是判据稳定，是概率。
- 与 §6/§7 的关系：§6 说「上限写在哪」，本节说「上限该随什么变」；共用**唯一事实源 = 注册源**，
  任何一侧写死在宿主脚本或 workflow 里都是第二份真相。
- 建议缺陷号 **658**（657 已被 M372「SNI 证书槽容量」占用；655 留 M208、656 为镜像新鲜度探针）。

### 8.1 反证（M375 发布轮实测，2026-11-05）：单看体积不足以解释 checkout 超时

| 观测 | M374（仓库 10.0 GB） | M375（仓库 **8.06 GB**） |
|---|---|---|
| el7 构建 job 检出 | 44m43s 未完成 ⇒ **cancelled** | **2m19s** 完成 |
| Tag Guard | **20.1 min cancelled** | **97 s success** |
| 整条 Release | 部分 job 失败/取消 | **12m29s，8/8 job 全绿** |

- 仓库 API `size` = **8,450,891 KB ≈ 8.06 GB**（缩小幅度 −19.5%），检出耗时却从「顶破超时」变为「分钟级」
  —— **减重 19.5% 不可能产生 10–20 倍的耗时差**。
- ⇒ 本节原叙「体积 × 并发克隆数共同决定检出耗时」中，**体积不是主导因子**；
  更可能是**窗口性 / 远端 pack 状态**（GitHub 侧 gc、pack 复用、并发拉取同一 pack 的排队）。
  **本轮无法进一步定因（不能控远端），故降级为「待证」。**
- **处置建议的效力随之降级**：
  - 保留：`filter: blob:none` 部分克隆 / 按需 `--depth=1` / 继续瘦身 —— 这些都是**独立的收益**（本机磁盘、传输量）；
  - 撤回：把它们当作「**已定位根因的修复**」来宣传。它们**未被证明**能消除 cancel。
- **仍然禁止**：靠反复重跑等它偶然过 —— 那只能证明「这次没撞上」，不构成判据稳定。
- 若要真定因，需要的最小证据是：同一 commit、同一 workflow、连续 ≥5 次运行，
  记录每次 checkout 的 `(开始时刻, 实耗, 是否复用 pack)` 并与 GitHub 状态页对齐。
  这条**尚未做**，故本节只写反证，不写新根因。
