# 字符串拼接 `+` / `+=` 的性能口径（M270）

> **一句话**：`s += "x"` 在 n=60 000 时是 **1.95 s**（`list.append` + `join` 是 13.8 ms，差 **141×**）。
> 本轮**只修了常数**（分配 2→1、整串拷贝 2→1），**复杂度未变**；
> 复杂度修不了的原因写在 §四 —— 那是**表示的硬约束**，不是没工夫优化。

---

## 一 量化（M266 本机复跑 · VM 轨产物 · 3 轮取 min）

| n | `s += "x"` | `list.append` + `join` | 差距 | 翻倍倍率 |
|---|---|---|---|---|
| 7 500 | 25.9 ms | 4.7 ms | 5.5× | — |
| 15 000 | 81.2 ms | 6.2 ms | 13× | 3.1× |
| 30 000 | 463.6 ms | 8.5 ms | 55× | 5.7× |
| 60 000 | **1 950 ms** | 13.8 ms | **141×** | 4.2× |

n 翻倍 ⇒ 耗时 ≈ 3–6× ⇒ **确证 O(n²)**；`append+join` 侧 4.7→6.2→8.5→13.8 = **线性**。
与晨曦实测（33 / 99 / 616 / 2 937 ms）**逐点同量级**。

**性质**：这是**运行时层**（`px_add` 的 STR+STR 分支），三条轨都受影响 ——
不是解释器的问题，也不是 VM 的问题。

## 二 修前路径（2 次分配 + 2×(la+lb) 字节拷贝）

```c
// runtime.c · px_add 的 STR+STR 分支（M270 前）
char* d = xmalloc(la + lb + 1);          // 分配 ①（中间缓冲）
memcpy(d, a.data, la);                   // 拷贝 ①
memcpy(d + la, b.data, lb);              // 拷贝 ②
d[la + lb] = 0;
LXValue r = px_str_len(d, la + lb);      // 分配 ② + 拷贝 ③（整串再来一遍）
xfree(d);
```

## 三 本轮改动（1 次分配 + 1×(la+lb) 字节拷贝）

新增 `px_str_concat2()` / `px_str_repeat()`：把两份数据**直接写进**
「`LXObject` + 内联 `data`」的**同一块内存**。

```c
// 单次分配：对象与数据在同一个 xmalloc 里（与 px_str_len_raw 布局逐字节一致）
LXObject* o = xmalloc(sizeof(LXObject) + (size_t)n + 1);
char* d = (char*)o + sizeof(LXObject);
if (la > 0) memcpy(d, sa, (size_t)la);
if (lb > 0) memcpy(d + la, sb, (size_t)lb);
d[n] = 0;
… o->as.str.{data,len,rune_len,offs_cnt,rune_offs} = …          // 与 px_str_len_raw 同款初始化
gc_register(o, sizeof(LXObject) + (size_t)n + 1);               // 同上尺寸
```

- `px_add` 的 STR+STR 分支 → `px_str_concat2`
- `px_mul` 的 STR×INT 分支 → `px_str_repeat`（**同族同形状**，一并收口）
- ⚠️ ISSUE28-B2 的「中间缓冲泄漏」在这条路径上**不再存在**（缓冲没了）；
  其它仍走 `px_str_len` 的站点照旧，那条修复本身仍然有效。

### 3.1 实测（本机 · VM 轨 · 3 轮取 min）

| n | 修前（M266） | **修后** | 提速 |
|---|---|---|---|
| 7 500 | 25.9 ms | **25.2 ms** | 1.03× |
| 15 000 | 81.2 ms | **72.6 ms** | 1.12× |
| 30 000 | 463.6 ms | **233.6 ms** | **1.98×** |
| 60 000 | 1 950 ms | **1 128 ms** | **1.73×** |

⇒ 大 n 段 **1.7–2.0×**（与「整串拷贝字节数减半」的预期一致）；
小 n 段几乎无变化（那时开销以「分配次数」为主，而分配只从 2 降到 1）。
**复杂度仍是 O(n²)** —— 见 §四。

**同族普查**（同一「中间缓冲 + `px_str_len`/`px_bytes_len`」形状）：
`bi_reversed`（7584）· `bi_bytes_set`（14126）· `bi_bytes_concat`（14170）· `bi_read_bytes`（14292）。
⇒ **都是一次性操作、不在循环里** ⇒ 性价比低，**本轮不动**（如实登记）。

## 四 ⚠️ 为什么**复杂度修不了**（这一节比改动本身重要）

### 4.1 表示：字符串数据**内联在对象里**，且**恒不可变**

```c
// runtime.c:3377 px_str_len_raw（唯一生产者）
LXObject* o = xmalloc(sizeof(LXObject) + (size_t)len + 1);
char* d = (char*)o + sizeof(LXObject);   // ← data 内联在对象之后（同一次分配内）
```

原文注释（**这是全仓不变量**）：

> 语义不变量：`PX_STR` 的 `data` **恒不可变**（全仓无任何就地改写 `as.str` 的站点）
> 且恒由本函数生产 ⇒ `px_obj_free` 的 `PX_STR` 分支不再单独释放 `data`。

⇒ 两条推论：

1. **就地扩容结构上不可能** —— 内联数组无法 grow；`realloc` 移动对象会让所有
   `LXValue.as.obj` 悬垂（`data` 是从 `obj` 算出来的）。
2. **`data` 不可变**是全仓依赖的不变量（`px_obj_free` 不释放 `data`、
   `px_str_const` 缓存、M106 的惰性 `rune_offs` 表都建立在它上面）。

### 4.2 CPython 的 `unicode_concatenate` **搬不过来**

CPython 之所以能「引用计数唯一 ⇒ 原地 `realloc`」，前提是**有引用计数**。
本运行时：

- **没有对象级引用计数** ⇒ 无法判定「唯一持有」
- `var x = s` 这种别名**没有任何记录** ⇒ 原地写会**静默改掉 `x`**
  （`px_add` 在 VM 轨是 `PXOP_ADD`、在 C 轨是 `fn_*` 里的表达式求值，
  两者都**拿不到**「这个值还挂在哪个槽上」的信息）

⇒ **正解只有两条**（都属独立立项）：

| 方案 | 内容 | 代价 |
|---|---|---|
| **A 引用计数** | 给对象加 refcount，`px_add` 在 `rc==1` 时原地扩容 | 触及全部创建/赋值/传参/容器站点；且 GC 是**标记-清除**（非 RC）⇒ 两套生命周期语义要协调 |
| **B 所有权/逃逸分析** | 编译器判定「该变量从未被别名化」⇒ 发专用 `STRAPPEND` 指令 | 需要真实的静态分析；且必须**保守**（假阳性 ⇒ 退回拷贝） |

⚠️ **本轮没有做，也没有把它写成"待办小事"** —— 它是**表示与生命周期语义的改动**，
按 M104/M72_PLAN 的既有口径属于「需先确认 compute-bound 需求才立项」的一类。

## 五 规避姿势（**现在就能用**）

```px
// ❌ O(n²)
var s = ""
for x in xs:
    s = s + str(x)

// ✅ 线性（n=30000 时快 ~45×；n=60000 时快 ~141×）
var parts = []
for x in xs:
    parts.append(str(x))
var s = join("", parts)
```

## 六 门与验收

- **三轨 stdout 一致**（VM / C / 解释轨）—— 拼接是纯数据操作，不涉语义
- M267 性能门**必须仍绿**（`fib28` / `while_sum` / `mixed` / `jsonwb` 双轨相对基线 1.0× ± 噪声）
- `rebake --check-all` 14/14（改 `runtime.c` ⇒ **必重烘**）+ `--check` 55 例 + `--check-vm` 镜像
- 发射冻结门：**不改发射** ⇒ 应逐字节不变（若红，说明我误动了解释器/编译器侧）

---

## 七 覆盖边界（如实登记）

- **复杂度未修**（见 §四）；本轮的收益是**常数**（分配 2→1、整串拷贝 2→1）
- 修的是 **`px_add` / `px_mul`** 两条**热点**路径；同族非热点四处**登记不动**（§三）
- 解释轨的**被解释程序**里的 `s + t` 走 `i_bin_add` 的 `Ok(l + r)`（= 解释器自身的字符串相加），
  其性能瓶颈**不在** `px_add` 而在逐节点求值 ⇒ 见 `docs/PX_RUN_FAST.md`
- **不覆盖** `bytes` 的拼接（`bytes_concat` 是另一条路径，本轮未动，见 §三 普查）
