# M108 二期预研 ①：握手锁（`g_srv_hs_mu`）争用量化 —— 实测报告

- 日期：2026-09-11 ｜ 执行：东月 ｜ 机器：dongyue（8 核 / 16G，load ≈ 0.2）
- 被测：`main @ ca128c7` 编译的 `px_serve` TLS 路径（RSA-2048 / EC-P256 自签证书）
- 资产：`examples/m108_lock/`（`m108_lock_daemon.px` / `go_bench.go` / `lockbench.sh` / `lockfutex.sh`）
- 隔离：服务端 `taskset 0-3`（4 核），客户端 `taskset 4-7`（4 核），互不抢核

## 0. 一句话结论

**握手热路径在任意并发下都只用满 ~1 个核（有效并发度 E ≈ 1.0），而同一套 serve 栈不握手时能到 3.3 个核。
按 futex 地址归因，串行点就是 `g_srv_hs_mu`：4.2s 窗口内 4917 次等待、累计 131.5 秒、
平均 30.9 个线程同时堵在它上面（共 75 线程）。按现测单次握手 CPU（RSA 8.73ms）计算，
该锁把握手吞吐钉在 ~114/s，而 4 核应有的上限是 ~458/s ⇒ 约 4.0× 无损可回收（8 核更多）。**

## 1. 指标定义（避免误读）

| 符号 | 定义 |
|---|---|
| `T_c` | 服务端处理**一次完整握手 + 该请求**的 CPU 秒（`/proc/<pid>/stat` 的 utime+stime 差分 / 次数） |
| `E` | **有效并发度** = 服务端 CPU 秒 / 墙钟秒。`E≈1` ⇒ 任何时刻只有一个核在干活；`E→4` ⇒ 4 核并行 |
| 锁上限 | 全局锁下 `rate_max = 1 / T_c_locked`；`N` 核理想值 = `N / T_c` |

`E` 是黑盒可直接测量、且不依赖任何内部埋点的量；**它同时给出"有没有串行"和"浪费了多少核"。**

## 3. 白盒：futex 按地址归因（`lockfutex.sh`）

`g_srv_hs_mu` 在静态非 PIE 二进制中地址固定（`nm` 取到 `0x78d540`），
故可用 `strace -f -T -e trace=futex` 抓全部 futex，再按 `uaddr` 精确归因。

| 场景 | 线程数 | 墙钟 | 服务端CPU | E | **目标锁 `0x78d540`** |
|---|---|---|---|---|---|
| **tls / RSA-2048** | 75 | 4.26s | 5.14s | 1.208 | **WAIT 4917 次 / 累计 131.52s / 均值 26.7ms / 最大 793.7ms / 平均同时阻塞 30.9 线程** |
| **plain（对照）** | 75 | 14.05s | 12.68s | 0.903 | **WAIT 0 次 / 累计 0.000s** |
| **tls / EC-P256** | 75 | 5.21s | 6.66s | 1.279 | **WAIT 9357 次 / 累计 151.01s / 均值 16.1ms / 最大 809.5ms / 平均同时阻塞 29.0 线程** |

交叉验证（防止归因错人）：同一窗口内**等待时间最长的地址**排序，tls/RSA 下 `0x78d540` 排第 1
（131.5s / 全部 futex 累计 328.7s = **40%**）；plain 下该地址**根本不出现在列表里**。

> `E` 略大于 1（1.21 / 1.28）自洽：HTTP 响应、I/O、accept 在**其他线程**并行，锁只覆盖握手段。

## 4. 单次握手的绝对成本（`lockfutex.sh` C 段，n=1200 conc=8）

| 路径 | 服务端 CPU / 次 |
|---|---|
| tls / RSA-2048 | **8.733 ms** |
| tls / EC-P256 | **4.325 ms** |
| plain（同栈不握手） | 0.325 ms |

由此推出的天花板：`1 / 8.733ms ≈ 114 次/s`（RSA）—— **与黑盒实测 94~128/s 逐点吻合**。
4 核理想 `4 / 8.733ms ≈ 458/s` ⇒ **≈4.0×**；全机 8 核理想 `≈916/s` ⇒ **≈8.0×**。

### 4.1 同一台机器、同样限 4 核的 openssl 基线（仅私钥运算）

| 运算 | openssl | 本栈（含协议栈） | 备注 |
|---|---|---|---|
| RSA-2048 sign | 1272/s（0.786 ms） | 8.733 ms / 握手 | 量级差距存在，但 mbedtls 纯 C 实现本就慢于 openssl 汇编路径 |
| ECDSA P-256 sign | 36545/s（0.027 ms） | 4.325 ms / 握手 | 同上 |

⚠️ **不下结论**：这组数字**不能**证明"mbedtls 预编译库未开优化"。
它与"mbedtls C 实现 + RSA blinding"的合理区间部分重叠。要判定必须重建对比（见 §6）。
此处如实登记，仅作为"重建时的顺手验证项"。

## 5. 这个锁为什么存在（不是 bug，是已登记的权衡）

`runtime/runtime.c:13919` 注释写明：随包 `mbedtls 3.6.2` **预编译库未启用线程支持**，
故 M101 起以**全局握手串行锁**保证并发握手正确性（M101 前置缺陷：并发握手共享私钥/session cache
导致 TLS1.3 CertificateVerify 签名错、TLS1.2 大并发 EOF）。
M108 已把持锁范围从"整个握手（含无超时阻塞读）"收窄到"每步持锁、步间放锁"，
所以现在的 E≈1 是**纯 CPU 串行**，不再包含 I/O 等待。

## 6. 二期判据（本报告的直接产出）

| 方案 | 预期收益 | 代价 / 风险 |
|---|---|---|
| **A. 去掉全局握手锁** | 握手吞吐 **≈4×（4 核）/ 最多 ≈8×（8 核）** —— 即上限从 114/s 提到 458~916/s | 必须重建 `libmbedcrypto/mbedtls/mbedx509`（**x86_64 + aarch64 + windows 三套**）开启 `MBEDTLS_THREADING_C` + `MBEDTLS_THREADING_PTHREAD`；**重建时须复跑 M101 并发握手 48×3 三轮**（那正是当初引入此锁的原因）；私钥/session cache 的**自有**共享结构仍需 `g_srv_tls_mu` 保护（锁要从"每步"进一步收窄到"仅注册/取用共享态"，不是简单删除） |
| **B. 保留锁，压低 `T_c`** | 未知（重建时顺手核优化级别即可测） | 与 A 共用同一次重建；风险更低，但收益上界受限于单核 |

**⇒ 建议**：A 与 B 一次做完（同一次库重建），用本目录的 `lockbench.sh` + `lockfutex.sh` 复测：
判据是 `E(conc=32)` 从 1.05 升到 ≥3.5，且 `examples/m101_s2/verify.sh` 三轮 FAIL=0。

## 7. 诚实边界（本报告的局限）

1. **strace 会显著拖慢被测进程**（plain 吞吐在 strace 下从 9257/s 掉到 285/s）。因此 §3 的绝对速率
   **不代表生产**；有效的是"地址归因结果"与"tls/plain 比值"。§2 的黑盒数据未挂 strace，速率可信。
2. `max_conn=64`、客户端 conc=32：已确认池不是瓶颈（同池 plain 可达 E≈3）。
3. 本机 8 核且非独占（load≈0.2，无编译任务并行）；未使用 `perf`（本机未安装），
   故无 cache-miss/指令级佐证，全部结论基于 CPU 时间与 futex 归因。
4. 长连接/keep-alive 场景不在本量化范围（每连接均强制全新握手，`SessionTicketsDisabled`）。
   真实 CDN 形态下复用率越高，本锁影响越小；但**每次冷启动/新连接**都仍受限。
