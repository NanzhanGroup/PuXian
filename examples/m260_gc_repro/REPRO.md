# M260 · 缺陷 267 家族 / M257 Heisenbug —— **复现装置与对照实验**

> 起源：**M257 §五**（2026-10-04）留下一条 ~1/60 的 Heisenbug ——
> 「容器在**仍在作用域内**时其存储被 GC 回收，随后被复用」⇒ 静默堆损坏；5 份 core 的
> 主形态是 `xfree ← px_dict_set+0x39894 ← bi_udp_recv`，指纹为
> `o->type == 5`（PX_BYTES）、偏移 16 的 `{4, -1}` = 同函数里 `px_bytes_len(buf, 4)`
> 造的 `"PING"` 4 字节对象。
>
> M257 同时写了两句诚实的话：
> ① **根因未定论**（已实测排除：类型白名单 ✓ · precise 精确根 ✓ · 主线程注册 ✓）；
> ② **「加任何探测器/守卫后 60~240 次均未复现」**。
>
> ⇒ 缺的不是又一次排查，而是**可重复测量的装置** + **说得清的对照**。

## 一 装置

* 探针：`examples/m256_eintr/probe_eintr.px`（M257 的原现场：多协程 + 高分配压力 +
  `udp_recv` 阻塞等待 + TCP 收发）。
* 三条判据（缺一不可）：
  1. **被信号杀死**（rc ≥ 128）；
  2. **输出缺 `M256-PROBE-DONE`**（跑不完）；
  3. **`[M257-CTR]` 命中**（M257 加的「容器存储失效」守卫 —— 它把静默损坏降级为**响亮**，
     所以**比崩溃更早暴露**，是本装置最有价值的一条）。
* 对照能力：`M260_WT=<另一棵树>` —— 「消失了」必须能区分「修好了」与「运气好」。

## 三 结论（**不冒充「已修」**）

1. 当前 HEAD 上 **0 复现**（A 20/20 · B 60/60）。
2. **但对照组 C（M256 树）同样 0 复现** ⇒ **不能把「消失」归因于 M258/M259 的修复**
   —— 若真是那两轮修复的功劳，C 组应当**至少复现一次**（M257 记录 ~1/60 ⇒ 60 次期望 1 次）。
3. 更可能的解释：该 Heisenbug **依赖当时的环境/时序条件**
   （与 M257 自己的记录一致：「加任何探测器/守卫后 60~240 次均未复现」）。
4. ⇒ **缺陷的复现条件仍未掌握**。本轮的贡献是**装置在手**：
   下一次任何一次复现，都会被上面三条判据**当场抓住**并留下日志；
   而**全量压力筛台账**（`selfhost/gcstress_ledger.tsv`）会把它记成 `FAIL_*` 而不放过
   —— M260 的完整一轮 423 条里 **`FAIL_*` = 0**（M207 基线是 5）。

## 四 覆盖边界（如实）

* 本装置只覆盖「**并发/挂起执行流 × 每次分配即 STW**」这一形态；其它 GC 形态由
  M170/M182/M183/M206/M209/M212/M213/M214/M257/M258/M259 各自的门覆盖。
* `PX_GC_INLINE=1` **不可省**（M206 纪律）：服务/spawn 模式下 GC 被延迟到安全点，
  只开 `PX_GC_STRESS` 时这类缺陷不显形（实测 collect 次数差一个量级）。
* ⚠️ **`PX_GC_INLINE=1` 会撞上已登记未修的缺陷 267 家族本身** ——
  故本门在遇到「被信号杀死」时**记数并响亮打印**，判据（rc=0 + 含 `DONE`）才是判红依据；
  这**不是**把崩溃当绿，而是「267 有自己的账」（M256 同款处置）。
* 探针用固定端口 `18420/18421` 与 `/tmp/px_m256_probe` ⇒ **不可并行跑**（本门串行）。
