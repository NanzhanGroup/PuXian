改动：`runtime/runtime.c`（M128 段：两阶段辅助 + 兜底开关 + 站点注入钩子；改写
`px_list_push` / `px_dict_set` / `gc_register`，并保留 `px_list_push_locked` /
`px_dict_set_locked` 两个锁内兜底函数）
例子：`examples/m128_unlock_grow/{unlock_grow.px, verify.sh}`（本门 **pass=62 / fail=0**）
前置里程碑：M125（分配失败分类）· M126（信号处理器隔离）· **M127（锁审计闸）**

## 1 病灶（两个）

**① 主病灶：持锁分配 ⇒ 只能 `_exit(1)`。** M127 门已把这条链坐实到调用链：

```
#0 __lll_lock_wait  #1 pthread_mutex_lock  #2 px_dict_set  #3 vm_run_loop  #4 coro_worker
```

三处在**持 `g_gc_mu`** 期间做可失败分配：

| 站点 | 可失败分配 | 触发时机 |
|---|---|---|
| `px_list_push` | `xrealloc(items)` | 每次容量翻倍 |
| `px_dict_set` | `xrealloc(keys)` ×2 + `xstrdup(key)` | 每次容量翻倍 / **每次新键** |
| `gc_register` | `xrealloc(g_objs)` | 对象表容量翻倍 |

M127 的审计闸保证「带锁回卷 ⇒ 留锁 ⇒ 假死」不再发生，但代价是这三处上的分配失败仍退回
`_exit(1)`（服务中断约 3 s，systemd 拉起）⇒ **本源要的「OOM ⇒ 请求级 500」在这些站点上
尚未成立**。

**② 次生病灶：失败的失败方式。** 原实现先 `cap *= 2` **再** `xrealloc`：

```c
o->as.dict.cap *= 2;                                              // ① 先改容量
o->as.dict.keys = xrealloc(o->as.dict.keys, sizeof(char*) * o->as.dict.cap);  // ② 可能失败
```

② 失败后会留下「cap 已翻倍、数组仍是旧长度」——**对象不变量被破坏**：下一次同长度的
`keys[len]` 写入落到数组之外 = **越界写**（静默堆破坏）。对请求内的临时对象后果有限，但对
长生命期对象（共享缓存字典、运行时对象表）就是真破坏。M128 的两阶段设计顺带修掉它：
备货**未发布即不可见** ⇒ 中途失败不改变对象状态。

## 2 修法：两阶段（锁外备货 → 锁内发布）

```
阶段 A（临界区外，可失败）   按无锁快照预判是否需要更大的数组 / 键副本，需要则先分配好
                              —— 失败发生在此 ⇒ **无锁在身** ⇒ 常规隔离 ⇒ 请求级 5xx
阶段 B（临界区内，不可失败） 只做指针发布（memcpy + 换指针 + 释放旧数组）；备货不足
                             （并发增长）则解锁重来，备货在锁外释放
```

要点：

- **备货是裸数组**（本线程私有、未发布）⇒ GC 不可见，任何中途失败都不影响对象。
- **旧数组仍在锁内释放**（与 `xrealloc` 语义一致），不改变既有的「谁能看见旧指针」安全论证。
- **热路径零额外开销**：不需要扩容时（绝大多数 push/set），阶段 A 什么都不做；`px_dict_set`
  命中已有键时仍只做 1 次加锁 + 1 次扫描 + **0 次分配**（与改动前一致）。
- `px_dict_set` 的插入路径需要键副本：先锁内扫描判定「键缺失」，再解锁备副本后重来；第二轮
  用 **len 快照复核（O(1)）**免去重扫 —— 依据是本仓字典**无删除路径**（键集单调，`len` 未
  变 ⇒ 期间没有插入发生）。
- **兜底（不回归、不无限循环）**：锁外重试 `PX_GROW_RETRY_MAX` 次（默认 32）仍不足 ⇒ 回退
  **锁内扩容**（= M127 及以前的行为，函数保留原样）。

**不变量为什么这样测**：子协程向**父协程持有的对象**追加 ⇒ 扩容分配被注入失败时子协程被隔离
终止，父协程继续 ⇒ 可直接核对「失败后对象是否完好、是否仍可用」。若沿用「先 `cap *= 2` 再
失败」的旧实现，父协程的后续追加会写越界（C6/C7 的 `tail`/`len=4097` 断言正是这一条）。

## 5 边界（如实，勿误读）

1. **只消除「这三处自身造成的」临界区分配**。若**调用方**另持一把运行时锁（例如模块在
   `g_ws_mu` / `g_sqlite_mu` 下调用 `px_dict_set`），失败时 M127 审计仍会介入 ⇒ `_exit(1)`。
   `m128_alloc` 的失败出口语义是「无锁在身 ⇒ 请求级 5xx」，不是「永远 5xx」。
2. **仍有锁内分配站点未清**（C9 实测；均已定位，非猜测）：
   `px_rate_limit_try`（请求路径，160 字节 / `g_rate_mu`）· `fserve_ensure`（首次 serve 入口
   初始化，2 次 `xcalloc` / `g_fserve_mu`）· `gc_init_env`（一次性的线程表 `xcalloc`，调用方
   持 `g_gc_mu`）⇒ 建议 M129。
3. **并发插入同一对象**：备货不足时会多走一次加锁（解锁重来）；`PX_GROW_RETRY_MAX` 用尽则退
   化为锁内扩容（不回归、不无限循环，但没有「锁外」保证）。
4. **`px_dict_set` 的 len 快照复核依赖「字典无删除路径」**。仓库当前确无删除 API（`grep`
   无 `px_dict_del`）；若未来引入删除，复核条件必须同步收紧（否则会误判「键缺失」而重复插入）。
5. 站点注入钩子 `PX_ALLOC_FAIL_SITE` 为**一次性**且环境变量**每次读**，仅测试用；
   `PX_ALLOC_FAIL_SITE_MIN` 设下限；生产不应设置（设置了也只是让扩容分配按注入失败）。
6. 注入钩子会给「关」状态加 ~2 次 `getenv`（只发生在扩容路径上），不影响非扩容热路径。

## 6 与 M127 门的关系（为什么 M127 门要加一个开关）

M127 门的关键用例（B/C）依赖「**持 `g_gc_mu` 时**分配失败」这条路径，而 M128 正是把这三处
的分配搬出了临界区 ⇒ **若不改，M127 门的 B/C 会不再命中**（这不是缺陷，恰是 M128 的成果）。
故 M127 门的 B/C 增加 `PX_GROW_RETRY_MAX=0`，**显式走兜底（锁内扩容）路径**来验收审计闸：
审计闸的职责是「万一还有锁内分配（含兜底路径与其它站点），绝不留锁假死」，它依然是必需品
（C9 就是默认路径上的一个真实例子）。
